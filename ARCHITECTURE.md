### Phase 5 — agent-issued magic link (`b527636`)

Agent mints a one-time login URL for its human operator without password/OAuth.

- Table `agent_session_tickets`: 32-byte token, 5-min TTL, `consumed_at`.
- Service `session-ticket-service.ts`.
- Exchanger `GET /api/auth/enter?t=<ticket>` (`auth.ts:188-229`). Validates → marks consumed → mints Lucia cookie → 302 to `/game`. Expired/consumed → 302 with `?error=expired-link` → `ExpiredLinkBanner` on landing.

### Phase 5.1 — wallet identity + 'scape portal

Three keypair roles per user, all ed25519:

```
users.id (UUID PK, stable)                  ← identity handle; never rotates
├── identity keypair
│    pub: users.identity_pubkey             ← rotatable
│    priv (primary): agent config           clawville:identity:<userId>
│    priv (backup):  users.identity_encrypted_sk (envelope-encrypted, support recovery only)
│    purpose: sign reconnect challenges; derives portal principalId
│
└── avatar wallet keypair (Solana)
     row: wallets{subject_type='avatar', subject_id=avatar.id}
     pub: wallets.public_key                ← mirrored to avatars.walletAddress
     priv (server): wallets.encrypted_secret_key  (envelope-encrypted under CF KEK)
     priv (human):  shown ONCE in first-connect response
     priv (agent):  never holds
     purpose: holds $CLAWVILLE; server signs custodially
```

Plus a **service issuer keypair** (singleton). Private key in Cloudflare Secrets Store; public published at `GET /.well-known/clawville-issuer.json`. Signs outbound partner calls. **Published purposes:** `partner-portal-issue`, `partner-portal-accept-link`, `partner-cognition-callback`, `partner-session-webhook`, and **`partner-launch-exchange`** (FIX-14, 2026-06-13 — signs the Hatcher owner-launch server-to-server exchange body in `partner-hatcher-launch.ts`). Relay note R8: `partner-launch-exchange` is only load-bearing if Hatcher's exchange verifier enforces signed-purpose scoping; today verification succeeds on pubkey match regardless of purpose, so this is a parity-safety add, not a fix to a current break.

**Reconnect (signed-challenge):** `POST /api/agent/challenge` → nonce → `POST /api/agent/reconnect { userId, nonce, signature: ed25519.sign(nonce, identityPrivKey) }` → mint session ticket. Wallet key never involved.

**Atomic identity bootstrap:** `UPDATE users SET identity_pubkey=$1, ... WHERE id=$2 AND identity_pubkey IS NULL RETURNING`. Race losers get `needsHumanReauth: true`.

**Envelope encryption (`keypair-vault.ts`):** each encrypted secret has a random 32-byte DEK; DEK is wrapped by Cloudflare-held KEK via the Worker at `CLOUDFLARE_WORKER_URL` (POST `/wrap`, `/unwrap`, bearer-authed). Hetzner never sees plaintext KEK. **Boot preflight (2026-06-15):** `CLOUDFLARE_WORKER_URL` + `CLOUDFLARE_WORKER_BEARER` are HARD-REQUIRED at startup — `apps/api/src/index.ts` asserts both are set on boot and `process.exit(1)`s (crash-loud, mirroring `FINGERPRINT_SECRET`) if either is missing, so a misconfigured box refuses to start rather than booting fine and failing on the first wallet op. The lazy `requireWorkerEnv` check inside `keypair-vault.ts` stays as defense-in-depth.

**Portal (ClawVille → 'scape):** `POST /api/portal/scape` → server builds canonical-JSON body → signs `sha256(body)` with service issuer SK → **SSRF-guards `SCAPE_HOSTED_SESSION_URL` via `validateOutboundUrlResolved` (DNS private-IP reject, no host allowlist — 'scape is not a Hatcher host; fail-closed 503 + `portal.scape.cross_failed{reason:'ssrf_blocked'}`)** → POSTs (`redirect:'error'`) to the validated URL with `X-Clawville-Issuer-Pubkey` + `X-Clawville-Signature` → emits `portal.scape.crossed` → returns `{ redirectUrl }`.

**Portal ('scape → ClawVille):** `POST /api/portal/mint-for-scape` — verifies `X-Scape-*` against `PARTNER_PUBKEYS.scape` allowlist env var, mints Phase 5 magic-link ticket.

**Account link (existing 'scape user):** `POST /api/portal/scape-link-code` (Lucia-authed) → user pastes in 'scape → `POST /api/portal/accept-scape-link` → consumes `pending_account_links` row atomically.

**Partner generalization (2026-06-01):** the inbound signature verifier is `verifyPartnerSignature(partnerId, …)` — `partnerId` selects the `PARTNER_PUBKEYS[partnerId]` allowlist entry; the ed25519-over-`sha256(rawBody)` crypto is partner-agnostic. Scape callers pass `'scape'`, Hatcher callers pass `'hatcher'`. `PARTNER_PUBKEYS` is a JSON map keyed by partner id, so adding a partner is one env key + four mirrored endpoints — no crypto change. **Cross-partner redemption fix (same diff):** both `accept-*-link` handlers now require `pending_account_links.remote_world` to equal the partner the endpoint serves, so a code minted for one partner can't be redeemed via another's endpoint; a mismatch returns the same opaque `link_expired_or_invalid` (404) as a missing code.

**Replay residual (FIX-9, 2026-06-13 — ACCEPTED, not a coded cache):** within the ±300s freshness window the same partner-signed bytes verify more than once (ed25519 over identical bytes verifies forever). This is a **documented, accepted residual**, not a hole: every partner write is **idempotent-by-agentId** (register/PATCH upsert the same row, DELETE no-ops once gone) so a replay yields no NEW effect, and the window matches Hatcher's agreed `authNonceExpirySecs:300` skew ceiling. A seen-signature cache was **prototyped and then REVERTED** (Codex review 2026-06-13): consuming a signature inside the verifier — before the route's durable outcome is known — would falsely `401 replayed_signature` a LEGITIMATE client retry after a 400/5xx/dropped response, a worse failure than the benign replay it blocks. **Future rule:** any NON-idempotent partner verb added later MUST carry proper replay protection at that time — a partner-supplied nonce bound into the signed challenge and consumed delete-on-read (mirror `consumeNonce` in `auth-challenge.ts`), gated on the route's durable success so a retry of a failed request is never mistaken for a replay. The verifier `verifyPartnerSignature` stays pure.

**Hatcher portal (partner #2, 2026-06-01 — `.claude/plans/hatcher-integration.md` §2):** a faithful mirror of the four scape endpoints. `POST /api/portal/hatcher` (Lucia, CV→Hatcher; signs + **SSRF-guards `HATCHER_HOSTED_SESSION_URL` via `validateHatcherProxyUrlResolved` — the SAME hatcher: host-allowlist + DNS private-IP guard the cognition path uses; fail-closed 503 + `portal.hatcher.cross_failed{reason:'ssrf_blocked'}`** — then POSTs (`redirect:'error'`) to the validated URL, relays the returned `sessionToken` into a `HATCHER_WEB_ORIGIN` redirect). `POST /api/portal/mint-for-hatcher` (Hatcher sig via `X-Hatcher-*`, same `principal:clawville:<uuid>` anti-enumeration regex, mints a `identityType:'portal-hatcher'` magic-link ticket). `POST /api/portal/accept-hatcher-link` (Hatcher sig; requires `remote_world='hatcher'`; writes `linked_hatcher_*` atomically). `POST /api/portal/hatcher-link-code` (Lucia; mints a pending link with `remote_world:'hatcher'`, 10-min TTL). Reuses `CLAWVILLE_SERVICE_ISSUER_SK/_PUBKEY` unchanged (one outbound keypair serves all partners). Per-IP rate limiters: portal 10/min, link-code 3/min. The outbound "Cross to Hatcher" frontend UI is deferred until Hatcher ships their session-issue endpoint.

# Hatcher / Realistic Character Pipeline (REBUILT 2026-06-18 — Meshy subscription + OpenAI, NO Blender, NO Mixamo)

**Status:** validated end-to-end on **Cronus** (user sign-off on look 2026-06-18). The 3 remaining Hatcher avatars (Helen, Clytemnestra, Phanes) run the same recipe.
**Supersedes:** the Tripo-via-fal + manual-Mixamo + Blender-finalize pipeline (the "SOLVED 2026-06-09" version). That whole path is DEAD — **Mixamo is removed from the pipeline** (user decision 2026-06-18: manual Mixamo rigging is unsustainable; it required me to do Blender work, which is banned). **No Blender step anywhere in the new pipeline.**

## Why this exists
We bought a **Meshy subscription** (MCP server `@meshy-ai/meshy-mcp-server`, key in `~/.itachi-api-keys` + `~/.mcp.json` as `MESHY_API_KEY`, ~3,100 credits). Meshy does mesh-gen AND auto-rig AND a 678-action animation library — the entire asset pipeline, no Blender, no Mixamo web upload. Animations are **Meshy-native clips** (baked on Meshy's own 24-bone rig), NOT Mixamo-retargeted.

## Lessons locked in 2026-07-23 (Biggie build) — BINDING on future characters

1. **Cross-view consistency beats per-view beauty.** The mesh QC failures traced to views disagreeing: open-toe sandals in 3q/back vs shoes in front (corrupt feet), a mesh-back trucker cap in the face view vs solid caps elsewhere (degraded the whole face reconstruction), shirt check-scale drift. Before the paid mesh step, diff the 4 views as a SET: same cap style + logo, same shirt pattern/scale, same footwear (CLOSED shoes — always prompt "NO sandals"), same jewelry, no props. One inconsistent view is a re-roll, not a shrug.
2. **T-pose strictness is mesh-QC-enforced, not eyeballed.** "Arms look extended" at 30° droop reads fine to the eye and ruins the rig (see the HARD GATE in step 4 and `fix-rig-tpose.mjs`). Prompt every full-body view with "PERFECTLY HORIZONTAL at exact shoulder height, elbows locked".
3. **Trademark/logo marks: never trust diffusion, never composite flat.** gpt-image renders an approximation every time (best case: gpt-image-2 + a bars-only transparent-PNG ref gets close); pasting the logo file onto the turnaround images reads as a sticker and was rejected on sight. The guaranteed path is post-rig **UV decal projection** into the baked texture: `scripts/hermes-pipeline/patch-cap-logo.mjs` (clusters the fragmented atlas islands near the target, erases the baked smear with the surface's own sampled tone, projects the exact PNG in 3D across UV seams). Budget for it from the start; don't burn re-rolls chasing a perfect baked logo.
4. **Identity anchoring recipe that worked:** real photo of the subject as ref #1 for every view; once a front is approved, EVERY other view regenerates with that front as a ref ("SAME character as the reference"); the face portrait must use ONLY the headshot + logo refs (full-body refs overpower portrait framing and you get another full-body) — then harmonize its headwear/shirt to the body views in a second pass if needed. `--model gpt-image-2` holds references distinctly better than gpt-image-1; use it for all identity-critical views.
5. **Meshy driver:** `scripts/hermes-pipeline/meshy-rest.mjs` (submit/status/download/rig/animate, task ids persisted to `tasks.json`) drives the subscription over plain REST — works in any session, no MCP server required. Bake results are stochastic: a clean re-bake can fix one artifact (waist smear) and a same-input re-bake can degrade another (face) — fix texture problems on the FINAL asset via the decal/repair scripts, not by re-rolling the bake.
6. **Exclusive-avatar mechanism (new pattern):** a model in `MODEL_REGISTRY` (renders, animates, `pickerHidden`) but deliberately ABSENT from shared `AGENT_MODELS` is API-unassignable by construction (zod refuses the key on every avatar route) and grantable only via manual `UPDATE avatars SET model_key='<key>'` — no code path can hand it out. `model_key` has no Postgres CHECK; the DB `avatar_type` column is vestigial (registry `avatar_type` drives rendering). First user: `biggie` (two accounts). Grant runbook: docker cp a pg script into the prod api container, `bun /tmp/grant-*.mjs`, always with before/after readback.
7. **Verification floors (process):** rig QC = animated FRONT-view idle+walk (`/preview/hermes?c=<slug>&az=270`); any re-baked asset at an unchanged URL gets a `?v` bump BEFORE re-verifying (a stale cache faked a failed fix); and remember headless-browser sessions you log into shared-world staging/prod are real presences — close them cleanly or they linger as ghost bodies.

## Lessons from the Hydra build (2026-10-31) — BINDING on future characters

1. **Credit cap in code.** `meshy-rest.mjs` refuses every paid command (`submit`, `rig`, `animate`) unless `MESHY_CREDIT_CAP=<owner-approved credits>` is set. The first paid call stores the account balance as `startBalance` in `tasks.json`. Each later paid call refuses when the credits spent since then plus the call's estimate (submit 30, rig 5, clip 3) exceed the cap. Hydra used 59 credits: mesh 30, rig 5, 8 clips 24.
2. **Owner-supplied turnarounds skip step 1.** When the owner gives finished T-pose views, copy them to `<slug>-turnaround/source/` unchanged and stage `openai/front.png`, `back.png`, `3q.png`. `face.png` is now OPTIONAL in `meshy-rest.mjs submit` (three views are enough; Meshy accepts 1 to 4).
3. **Rig height is a parameter:** `meshy-rest.mjs rig <slug> [height_m]` (1.0 to 2.6 m; default 1.85). Hydra: 1.75.
4. **Hard gate in practice.** Hydra's mesh read armspan/height 0.892 although the arms look horizontal in the images. `fix-rig-tpose.mjs` measured only about 6 degrees of droop per arm and set both to exact ±X. Run it on every Meshy rig, not only after a visible droop.
5. **Served file = `-w30k.vrm`.** After `assets-optimize.ts <file>`, decimate with `scripts/decimate-vrm.ts <in.vrm> 0.26 <out-w30k.vrm> --target-tris 30000 --error 0.001 --weld-islands` (the Ansem and Adinero recipe). A mesh with very many UV islands (Hydra: 2,250 islands, long strand hair) floors near 49k to 54k tris in `--weld-islands` mode at every error bound. In that case, run plain mode (`--target-tris 30000 --error 0.003`, no `--weld-islands`). Then compare source and output renders side by side before you ship it. Hydra plain 30.3k tris showed no visible seam smear. Gate both with `bun scripts/vrm-pipeline-validate.mjs <source.vrm> <out.vrm> --expect-quantize` (only the decimation-inherent S3.0 may fail).
6. **Headless QC renders without a browser extension.** `<slug>-mesh/meshy-openai/_shot.html?src=<glb-or-vrm>&az=<deg>` (model-viewer with the meshopt decoder set, so optimized VRMs load) plus a raw CDP driver (Node 24 built-in WebSocket + headless Chrome, `Page.captureScreenshot` after `model-viewer.loaded`). Chrome's `--screenshot` flag captures BEFORE the model loads and gives blank frames.
7. **Round 2 (owner key art).** Round 1 hid the eyes: the owner's views drew bangs over the eyes, and Meshy's remesh smoothed what was left. `hydra-turnaround.mjs` (gpt-image-2, dollar cap in code via `OPENAI_IMAGE_CAP_USD` and `openai-v2/spend.json`, $0.40 booked per call against a real cost of about $0.25) anchors the body views to an owner-picked body reference and the owner's key art (`source/site-ref.png`), and the face view to the key art only. The identity text says "bangs swept aside, NEVER over the eyes". The eyes then survived the mesh. Two cross-view faults showed up and each cost a re-roll: hair crests in the face view only, and high heels in the 3/4 and back views only. Prompt "FLAT-SOLED boots, NO heels" and "NO hair ornaments" from the start. `meshy-rest.mjs` takes `MESHY_VARIANT=v2` to read `openai-v2/` and write `meshy-openai-v2/` with its own credit ledger.
8. **Meshy emissive is a full-texture copy.** Every Meshy rig so far (Adinero, Ansem, Biggie, Helen, Hydra round 1) has `emissiveTexture` = a dim copy of the whole base color at `emissiveFactor [1,1,1]`. Light materials (white hair) look washed out, and nothing glows more than anything else. For a character that must glow, run `bun scripts/hermes-pipeline/glow-map-from-basecolor.mjs <rigged-tpose.glb> <rigged-glow.glb> [hueMin hueMax satMin valMin boost]` BEFORE VRM inject. It keeps only saturated neon texels (Hydra: hue 185-230, sat >= 0.6, val >= 0.5, 1.8% of texels), dilates and feathers them, and writes ONE fixed neon color (PNG) as the emissive map. Two failed variants: copying the baked texel was too dim after tone mapping, and normalizing each texel to full value turned grey armor highlights under the feathered edge into white blotches. Looser thresholds (sat 0.45, val 0.35) lit blue reflections on the armor in blocks.
9. **Bench page.** `bun scripts/hermes-pipeline/strip-meshy-clips.mjs <model.vrm> <animDir> <outDir>` writes a meshopt-decoded `model.glb` and animation-only clips (about 3.5 MB in total for 10 clips) that bind to the model by bone name. The artifact host does not serve `.glb`, so the Hydra bench ships them as base64 text files.
10. **Per-character asset repair runs on the source GLB, never on the VRM (2026-11-01).** `node scripts/hermes-pipeline/hydra-face-fix.mjs <rigged-glow.glb> <rigged-face.glb> apps/web/public/avatars` runs between `glow-map-from-basecolor.mjs` and `inject-vrm-meshy.mjs` (gltf-transform drops the VRMC block, so it refuses a `.vrm`). It fixed four founder findings, each selected by rest-pose 3D position, not by UV, because Meshy splits small features over many UV fragments: (a) the -X face looked dented. The depth differed only 1-2 mm, but the vertex normals were noisy. Each -X face vertex takes the mirrored position and normal of the closest +X face point, feathered at the edge, and hair strands (no match within 4 mm) are skipped. (b) The -X eye was split over dark UV fragments. Its triangles get new corner vertices with UVs mirrored from the clean eye. (c) The earpiece cups get suit black for skin-tone and grey texels. (d) The chest H strokes are near-white and the glow map missed them; the H and the eyes are added to the emissive mask at full neon. Step 5 bakes the halo masks that `lib/three/hydra-halo.ts` reads. Trap: sharp returns 3 channels for 1-channel raw input, so every grey read needs `.extractChannel(0)`. Without it the bake read interleaved RGB as grey and lit hair instead of the H. Then re-run inject, optimize, decimate (plain mode) and validate, and bump the VRM `?v=N`.

## Animation library (Meshy)
- 678 actions. There is **no list-endpoint** in the API — the catalog is the docs page `https://docs.meshy.ai/en/api/animation-library` (a `<table>`; parse `action_id`→name). A snapshot lives at `/tmp/meshy_actions.json` during a session; re-fetch if stale.
- **Gaps Meshy does NOT have (and Mixamo is banned, so no fallback):** `skateboarding` / `surfing` (none — closest are `390 Stand_on_Pole_and_Balance` / `516 slide_light`, both rejected on Cronus 2026-06-18), `flying`/`hover` (none clean), `praying` (none). These are per-character *specials* the legacy avatars have for their themes; absent slots fall back gracefully. Revisit per-avatar only if one genuinely needs it (e.g. Reef Race surf — deferred, reef race isn't done).

## Jewelry / fine-accessory rule (still applies — i2m limitation, not tool-specific)
Thin ornate metal (forehead circlets, diadem filigree, fine chains) does **not** survive image-to-3D — every tool melts it into a soft raised band. Re-rolling does NOT fix it. The old fix was modeling it in Blender + weighting to `Head` — but Blender is banned now, so for the Meshy pipeline: accept the melted band, or design the character so fine metal isn't load-bearing. Never texture-repaint a flat accessory ("shoes are just a texture on the leg" was rejected).

# opus-D3 — BACKEND / API / DB INTEGRITY + PARITY — Forensic Audit

## Summary
Overall the backend is in strong shape. The auth/identity core (`require-auth-or-agent.ts`) is exceptionally well-hardened (fail-closed liveness gate, rotation invalidation, rebind-theft backstop, guest→non-ledger demotion) and the E5 parity discipline is genuinely applied across the money/state routes that matter most: items, quests, bounties, land, exchange, activities, special-events, and x402-checkout all resolve a connected/hosted agent as a first-class subject with `ledgerCapable`/`requireNonGuestIdentity` gating. Leaderboard weights and daily caps match the spec EXACTLY (chat 10 / collab 40 / building 3 / skill 1 / connected 1 / identity 5 / activity 12·6·3·1; caps 50/50/10/11/10) with `LEAST(count,cap)` capping, bot filtering, house-agent exclusion, and a durable frozen-`subject_was_guest` guest carve-out. The avatars schema enforces the vCLAW sum via a DB CHECK plus unique/category/harness constraints, and I found **no direct balance-column faucet** in any D3 route (the only raw `avatars.claw_tokens` write is the intentional off-ledger guest-demo debit in `items.ts`, which decrements `soft_balance` in lockstep to satisfy the CHECK). IDOR is properly guarded (party-leader enqueue, cosmetic-ownership-scoped equip, avatar-scoped-by-`user.id` writes, no body-supplied avatarId on money paths).

**Worst issue:** the cosmetic shop's **vCLAW-balance purchase + equip is human-only** — a connected/hosted agent cannot spend its earned vCLAW on a cosmetic or equip one it owns, an E5 economy/state parity gap that E5 itself says must be fixed, not documented-and-walked-past.

**Headline counts:** BLOCKER 1 (cosmetics vCLAW purchase parity), HIGH 2 (cosmetics equip/unequip parity; tutorial-claim earn parity — known debt), LOW 2 (Nori system-chat scores as teacher-chat on the public board; bare `c.req.json()` → 500 on malformed body).

## Findings

### [BLOCKER] E5 parity gap — cosmetic vCLAW-balance purchase is human-only — `apps/api/src/routes/cosmetics.ts:386`
- **What the code does:** `POST /:skuId/buy` is gated `sessionMiddleware, requireAuth, requireNonGuestUser` and reads the subject from `c.get('user')` only. It spends real vCLAW via `debitClawTokens({ ..., actorKind: 'human' })` (`cosmetics.ts:445`) and credits the house treasury. There is no `X-Clawville-Agent-Session` resolution, cosmetics is NOT in the `[ACTION:]` whitelist (`npc-simulation.ts` verbs = move/emote/enter_building/enter_cove/enter_poker_room/talk_to_npc), and the agent gateway's `buy` tool fulfils the ITEM shop, not skins (grep for `cosmetic`/`avatarSkins` in `agent-gateway.ts` = none).
- **Why it's wrong/risky:** the cosmetic shop is an economy feature that spends vCLAW; per Rule E5 every such feature MUST be reachable by a connected/hosted agent settling to its own avatar. The ONLY agent-reachable cosmetic path is the separate `x402-checkout` USDC on-ramp fulfiller (`x402-checkout.ts:66` → `checkout-fulfillers/cosmetic-purchase`), which is (a) a DIFFERENT rail (pay fresh USDC, not debit the avatar's earned vCLAW balance) and (b) currently `503 on_ramp_unconfigured` (`x402-checkout.ts:7`, FEATURE_GATE, no live value). So an agent that earned vCLAW from bounties/activities/land has NO way to spend it on cosmetics the way a human can. The brief scores an economy write that only does `requireAuth`/user-XOR-guest as a BLOCKING parity defect; E5's own retroactive-debt clause says any later-found human-only economy feature is "a bug to FIX, not to document and walk past."
- **Failure scenario:** hosted agent accrues 500 vCLAW winning activities → tries to buy a 200-vCLAW hat → no endpoint accepts its session for a vCLAW-balance debit; the human next to it buys the same hat from its balance. Parity broken on a live economy surface.
- **Fix:** switch `/:skuId/buy` to `requireAuthOrAgentSession` + `requireLedgerCapableIdentity` (mirroring `items.ts /buy` and `special-events` `resolveSignupSubject`), resolve `identity.avatarId`, and set `actorKind` from `identity.kind`. Keep the guest→demo branch (guest-owned agents already demote to non-ledger in `resolveAgentSession`). Add a PARITY note. Real-world blast radius is cosmetic-only, but the gate is mechanical.

### [HIGH] E5 parity gap — cosmetic equip/unequip is human-only — `apps/api/src/routes/cosmetics.ts:353,358`
- **What the code does:** `POST /:skuId/equip` and `/:skuId/unequip` are `sessionMiddleware, requireAuth` only; `setEquipped(c, skuId, user.id, …)` (`cosmetics.ts:313`) resolves the avatar from `user.id`.
- **Why it's wrong/risky:** equipping mutates user-facing avatar appearance/state. Even if the purchase gap above is fixed, an agent that owns a skin (e.g. granted via the USDC fulfiller or a future agent buy) cannot equip/unequip it — no agent-session path exists. Other-state parity gap per the brief.
- **Failure scenario:** agent owns an aura skin, cannot render it; the in-world visual state a human controls is unreachable to the agent for its own avatar.
- **Fix:** accept `requireAuthOrAgentSession` and pass `identity.avatarId` into `setEquipped` (the ownership filter `avatarSkins.avatarId == avatar.id` already prevents IDOR for either subject).

### [HIGH] E5 parity gap — tutorial-quest reward earn path is human-only (known debt) — `apps/api/src/routes/quests.ts:1401`
- **What the code does:** `POST /tutorial/:id/claim` is `requireAuth` only; guest-blocked (`quests.ts:1425`); credits real vCLAW (~175 total across the ladder) via `creditClawTokens(reason:'tutorial_quest')` inside a tx, idempotent on unique `(user_id, quest_id)`, gated by a server-side engagement validator. It is well-built in isolation.
- **Why it's wrong/risky:** it is an economy EARN path with no connected/hosted-agent equivalent — a hosted agent cannot complete the onboarding ladder to earn the same CT. This is the documented "P2b tutorial-ladder parity debt" (MEMORY.md, economy-audit-fixes), so it is a known gap, not a regression. Included for completeness of the E5 sweep.
- **Failure scenario:** two identical new participants, one human one hosted agent; only the human can claim ~175 CT of onboarding rewards.
- **Fix:** either (a) build an agent-reachable tutorial-completion path (agent identity + agent-appropriate engagement proofs), or (b) formally scope the tutorial ladder as human-onboarding-only in E5 and neutralise it from the parity contract. Do not leave it as silent asymmetry.

### [LOW] System-agent (Nori) chat scores on the public leaderboard identically to teacher chat — `apps/api/src/routes/chat.ts:147` + `leaderboard.ts:588,719`
- **What the code does:** `POST /chat/system/:slug` emits `eventType:'agent.chat.turn'` with `payload.chatType:'system-agent'` on EVERY turn (the CT reward is 1/60s-limited, but the EVENT is not). The leaderboard daily-cap CTE counts ALL `agent.chat.turn` at `teacherChat` weight (10), cap 50/day, WITHOUT filtering on `chatType`.
- **Why it's risky:** the code deliberately tags system chats distinctly and excludes them from the `/dash` teacher-chat metric (`chat.ts:156`), but that exclusion does NOT extend to leaderboard scoring — so Nori chats rank exactly like real teacher knowledge-transfer chats (up to 50×10=500 rank-points/day). Bounded by the 50/day cap + one LLM call per turn, so low impact, but it is an inconsistency between the two scoring surfaces and lets a subject pad the learning-weighted board with orientation chatter.
- **Failure scenario:** a subject loops 50 one-word Nori messages/day → +500 leaderboard points at the "learning event" weight, none of which is teacher knowledge transfer.
- **Fix:** if system-agent chat should not count as a learning event, add `AND coalesce(payload->>'chatType','') <> 'system-agent'` to the `agent.chat.turn` FILTERs in both `agent_daily` and `avatar_daily` CTEs; otherwise document that any `agent.chat.turn` (incl. Nori) is intentionally rank-bearing so the two surfaces are reconciled.

### [LOW] Bare `await c.req.json()` throws 500 on malformed body on several mutating routes — `avatars.ts:172,508,922,1136,1448`; `chat.ts:54,182`; `items.ts:72,298`; `quests.ts:253,362,435,857`; `locations.ts:67`
- **What the code does:** these handlers call `await c.req.json()` un-guarded, then `safeParse`. If the body is not valid JSON, `c.req.json()` throws BEFORE Zod runs and the request 500s via the global `onError` instead of a clean 400.
- **Why it's risky:** low — Zod still guards SHAPE once JSON parses; this is only the malformed-JSON edge. But it muddies error semantics (500 vs 400) and inflates error alerting. The `.catch(() => ({}))` variants (`avatars.ts:1320`, `activities.ts:264/430/470`, `users.ts:83`) already do the right thing.
- **Fix:** standardise on `const body = await c.req.json().catch(() => null)` then `if (!body) → 400`, or a shared `parseJsonBody` helper, so a malformed body is a deterministic 400.

## Governing invariants (enforceable rules that should bind every future change to this subsystem)
1. **WHEN** a route mutates economy or user-facing avatar state (spend/earn vCLAW, buy/equip cosmetics, quests, land, exchange, bounties, activities), the change MUST gate on `requireAuthOrAgentSession` (+ `requireLedgerCapableIdentity`/`requireNonGuestIdentity` for real settlement), resolve the subject from `c.get('identity').avatarId`, set `actorKind` from `identity.kind`, and carry a PARITY note — a bare `requireAuth`/`requireNonGuestUser` gate on such a route is an automatic BLOCKING parity defect (incl. the cosmetic shop).
2. **WHEN** vCLAW balance changes, the write MUST go through `claw-token-ledger` (`debit/creditClawTokens`), never a direct `avatars.claw_tokens`/tag-column write — the SOLE exception is the off-ledger guest-demo path, which MUST decrement `claw_tokens` and `soft_balance` together under `FOR UPDATE` to keep `avatars_vclaw_balance_sum` satisfied and MUST write no ledger row.
3. **WHEN** the leaderboard scoring CTE, weights (`AGENT_SCORE_WEIGHTS`/`ACTIVITY_PLACEMENT_WEIGHTS`), or caps (`DAILY_CAPS`) change, they MUST stay identical to the CLAUDE.md Brand Identity table, keep `LEAST(count,cap)` per (subject,day), and preserve the bot (`subjectType != 'bot'`), house (`is_house` JOIN), and guest (`subject_was_guest` frozen + live-`is_guest` NULL backstop) exclusions.
4. **WHEN** a new leaderboard-eligible event type is emitted (e.g. a new `agent.chat.turn` sub-kind), the scoring CTE FILTERs MUST be updated in the SAME diff to explicitly include or exclude it — an event that silently inherits an existing weight (as `chatType:'system-agent'` inherits teacher-chat) is a scoring drift.
5. **WHEN** a mutating handler reads a JSON body, it MUST parse defensively (`.json().catch(() => null)` → 400) so malformed input is a deterministic 400, never a 500.
6. **WHEN** a handler updates the `avatars` row, the update set MUST be constructed field-by-field from Zod-validated data (never spread raw client body) and scoped by `user.id`/`identity.avatarId` — never a client-supplied avatarId on a state/economy write.
7. **WHEN** any agent-session-trusting path is added, it MUST route through `validateLiveAgentSession`/`resolveAgentSession` (never bare Map membership) so the TTL, rotation, rebind, and guest gates apply uniformly.

# opus-D4 — AGENT RUNTIME, ElizaOS, PROTOCOL PARITY — Forensic Audit

## Summary
Overall health of the D4 surface is **good**. ElizaOS is genuinely load-bearing (not a stub): `eliza-runtime.ts` constructs the real `@elizaos/core` `AgentRuntime`, calls `runtime.initialize()`, `generateText()`, `useModel()`, and `createMemory()`; avatar + teacher/location chat all route through `runtime.processMessage`. The in-world `[ACTION:]` executor (`npc-simulation.ts executeHatcherAction`) is a correct hard gate — prototype-key-safe, bounds-clamped, DoS-capped, proximity-gated, default-drop — and its 6 verbs are in exact parity with the §3a protocol manual, with `PROTOCOL_VERSION=18` and a disciplined bump history. Hosted-agent autonomy is real and wired (perceive→decide→act via ElizaOS `useModel`, settlement through `world-teacher-chat.ts`, earned-skill RAG memory). The three-surface game-flow sync (Nori `knowledge[]` / SKILL.md / hosted `createMemory`) is unusually well-maintained.

**Worst issue (HIGH):** there is a *second*, undocumented, un-version-tracked `[ACTION:]` executor — `eliza-runtime.ts processMessage`/`executeAction` against `clawvillePlugin.actions` (8 economy/utility verbs) — reachable by connected/hosted agents. It shares the identical `[ACTION: NAME(...)]` grammar but escapes the CLAUDE.md whitelist-parity governance that only names `npc-simulation.ts`, and the manual actively tells agents "economy never flows through the free-text action parser," which is false for `ACCEPT_QUEST`/`SUBMIT_QUEST` (they execute).

Headline count: **1 HIGH, 2 MEDIUM, 2 LOW.**

## Findings

### [HIGH] Second, ungoverned `[ACTION:]` executor (processMessage/clawvillePlugin) — parity + framework-honesty gap — `packages/agent-runtime/src/eliza-runtime.ts:1123-1204,1298-1366`
- **What the code does:** `processMessage` builds an action-description block for the LLM (`buildActionDescriptions`, :1106) whenever `state.services` is present, then parses the model's reply with the SAME grammar as the in-world gate — `parseActionInvocations` regex `/\[ACTION:\s*(\w+)\(([^)]*)\)\]/g` (:1132) — and executes matches against `clawvillePlugin.actions` (`packages/agent-runtime/src/actions/index.ts` → 8 verbs: `BUY_ITEM`, `LEARN_SKILL`, `CLAIM_BOUNTY`, `ACCEPT_QUEST`, `SUBMIT_QUEST`, `CHECK_BALANCE`, `LIST_BUILDINGS`, `VISIT_BUILDING`). Several mutate economy state — e.g. `BUY_ITEM` debits vCLAW (`actions/buy-item.ts:123 debitClawTokens`), `CLAIM_BOUNTY` writes `bountyAttempts` + increments the bounty (`actions/claim-bounty.ts:147-167`), `ACCEPT_QUEST`/`SUBMIT_QUEST` write `questSubmissions`. This path is reachable by **connected/hosted agents**, not just human chat: `apps/api/src/routes/agent-gateway.ts:2252,2266` passes `services` into `processMessage` for a connected agent's NPC-chat turn (also `openclaw.ts:592,740`).
- **Why it's wrong/risky:** CLAUDE.md's "Hatcher action whitelist parity" rule is mechanical and names exactly ONE executor as the authoritative gate (`npc-simulation.ts dispatchHatcherActions/executeHatcherAction`) that must stay in parity with the §3a manual and bump `PROTOCOL_VERSION`. This second executor emits the identical `[ACTION:]` grammar, executes agent-invocable economy verbs, and is (a) **not documented in the §3a whitelist** (`skill-protocol.ts:397-421` lists only the 6 world-motion verbs), (b) **not tracked by `PROTOCOL_VERSION` parity**, and (c) **directly contradicted by the manual's own copy** — §3a: "Your brain's ONLY action channel is emitting `[ACTION: verb(args)]` tags" (the 6), and §7/§8/§13/§14 repeatedly assert "real vCLAW … never the free-text action parser." `ACCEPT_QUEST`/`SUBMIT_QUEST` DO execute through the free-text parser (they have a `getParam('questId')` short-circuit in `validate`, so they are live — see MEDIUM below). The manual §12 mentions `ACCEPT_QUEST`/`SUBMIT_QUEST` as "native conversation actions" for hosted agents but never ties them to the `[ACTION:]` grammar, the whitelist, or the version-parity discipline.
- **Failure scenario:** A hosted/connected agent's cognition reply contains `[ACTION: ACCEPT_QUEST(questId=<uuid>)]`. `processMessage` parses and executes it against `state.avatarId` (the responding runtime's own avatar), mutating quest state — a free-text-triggered economy write the agent was never told exists and the manual said was impossible. Because a new economy `[ACTION:]` verb can be added here with no §3a edit and no `PROTOCOL_VERSION` bump, the two surfaces silently drift and connected agents are mis-taught the contract. (Blast radius is bounded: `avatarId` is server-set to the caller's own runtime avatar, not taken from the tag, so there is no cross-avatar drain — hence HIGH, not BLOCKER.)
- **Fix:** Bring this executor under the same governance: either (a) document the live subset (`ACCEPT_QUEST`/`SUBMIT_QUEST`) as part of the versioned action contract in §3a/§12 with a `PROTOCOL_VERSION` bump and add it to the whitelist-parity harness, or (b) route these through the same central whitelist/version constant used by `npc-simulation.ts`. Add a CLAUDE.md note that `eliza-runtime.ts processMessage` is a second `[ACTION:]` executor bound by the parity rule. Correct the manual's absolute "never the free-text action parser" phrasing.

### [MEDIUM] 6 of 8 plugin actions are dead via the `[ACTION:]` structured-invocation path — `validate()` gates on the synthetic message's empty text — `packages/agent-runtime/src/eliza-runtime.ts:1182-1192`
- **What the code does:** `executeAction` constructs the invocation message as `{ content: { text: '', parameters: params, … }, … }` (:1182) — **empty `text`**, real `parameters`. It then calls `action.validate(runtime, message, state)` and, on a falsy return, **skips** the handler (`if (!isValid) { … return null; }` :1188-1190). `getMessageText` returns `message.content.text` = `''` (`actions/types.ts:117-122`). Of the 8 actions, only `ACCEPT_QUEST` and `SUBMIT_QUEST` were given a structured-path fix — `if (getParam(message,'questId')) return true;` (`actions/accept-quest.ts`, `actions/submit-quest.ts`, labeled "Codex round 4"). The other six — `BUY_ITEM`, `LEARN_SKILL`, `CLAIM_BOUNTY`, `VISIT_BUILDING`, `CHECK_BALANCE`, `LIST_BUILDINGS` — `validate()` only tests keyword membership in the (empty) text, so they return `false` and are silently skipped.
- **Why it's wrong/risky:** The intended invocation IS the tag/structured path (the accept-quest comment states it explicitly). Six actions the prompt advertises to the model (`buildActionDescriptions`, :1106) are unreachable via that path: the model emits `[ACTION: BUY_ITEM(itemId=…)]`, the tag is stripped from speech (:1354), no handler runs, and the surrounding prose the model wrote (e.g. "Purchased!") is returned as-is — the user/agent is told an action happened when it did not. No money is lost (the debit never fires) but the chat-driven shop/bounty/learn features are non-functional and misleading.
- **Failure scenario:** Human tells their avatar-agent "buy the Cron Scheduling book." `processMessage` receives content `"buy the …"`, the LLM replies `"[ACTION: BUY_ITEM(itemId=cron-automation-basics)] Done — enjoy!"`. `parseActionInvocations` extracts `BUY_ITEM`; `executeAction` validates against `text:''` → `'buy'∈''` false → skipped. Reply returned: "Done — enjoy!" No book purchased, no debit, no inventory row. Silent feature failure.
- **Fix:** Apply the same `getParam`-first short-circuit the quest actions use to the other six `validate()` functions (a present required param IS the structured-intent signal), or have `executeAction` pass the ORIGINAL user turn text into the synthetic message so keyword `validate()` still fires. Add a test asserting each plugin action executes via `[ACTION:]`.

### [MEDIUM] `processMessage` action executor has NO per-reply action cap — asymmetric with the documented "≤4 per reply" bound — `packages/agent-runtime/src/eliza-runtime.ts:1338-1350`
- **What the code does:** The dispatch loop iterates over EVERY parsed invocation with no ceiling: `for (const invocation of invocations) { const actionResult = await this.executeAction(...) }`. By contrast the in-world executor caps at `MAX_HATCHER_ACTIONS_PER_REPLY = 4` (`npc-simulation.ts:144,1612-1617`) and the §3a manual promises "At most 4 actions execute per reply."
- **Why it's wrong/risky:** A hostile or hallucinating model reply carrying many `[ACTION:]` tags runs an unbounded number of handler executions (each may issue DB round-trips) on the request thread — a per-request cost/DoS asymmetry, and a contract mismatch with the documented bound agents are told to rely on. Live impact is currently muted because only the 2 quest actions execute (see MEDIUM above) and they are idempotent-ish, but the cap should not depend on that accident.
- **Fix:** Apply the same `MAX_*_ACTIONS_PER_REPLY` cap in `processMessage`'s dispatch loop; share the constant with `npc-simulation.ts`.

### [LOW] `agent-substrate-client`/ambient-banter cognition for hosted agents bypasses ElizaOS by design — verify it is intended — `apps/api/src/services/npc-conversation-engine.ts:21-35,163+`, `npc-simulation.ts:2866-2890`
- **What the code does:** Ambient NPC↔NPC banter for pure NPCs calls OpenAI directly via the InferenceRouter `default` route (`npc-conversation-engine.ts:30-31 callOpenAIForNpc`) — NOT ElizaOS. Agent legs (`hatcher-proxy`, `hermes-local`) route cognition through `AgentSubstrateClient.chat` (the partner gateway / substrate), and their `[ACTION:]` tags are dispatched through the governed `dispatchHatcherActions` executor (`npc-simulation.ts:2883-2886`).
- **Why it's (probably) fine but worth flagging:** CLAUDE.md's "ElizaOS is MANDATORY" applies to **avatar + location/teacher chat + the orchestrator** — those DO use `createElizaRuntime`/`processMessage` (`avatars.ts:1226`, `world-teacher-chat.ts:242`, `chat.ts`). Ambient NPC banter is the explicitly-carved-out "town-liveliness layer," and BYO/proxy agents legitimately use their own brain, not ElizaOS. So this is not a clear violation — but the direct-OpenAI ambient path plus the substrate-client agent path are two non-ElizaOS cognition surfaces; confirm the mandate's scope covers only the chat/orchestrator surfaces and record it, so a future reader does not mistake "NPC banter via OpenAI" for a stubbed-out ElizaOS.
- **Fix:** None required if intended; add a one-line note to `ARCHITECTURE.md §6`/CLAUDE.md that ambient NPC banter and BYO/proxy agent cognition are intentionally off the ElizaOS runtime, and that the mandate binds only avatar/location/teacher chat + the orchestrator.

## Governing invariants (enforceable rules that should bind every future change to this subsystem)
1. **WHEN any code parses the `[ACTION: verb(args)]` grammar and executes verbs**, the change MUST register that executor under the single whitelist-parity governance: its verb set MUST be documented in `skill-protocol.ts` §3a (or a named sibling section), tracked by `PROTOCOL_VERSION`, and covered by the mock-Hatcher/self-test harness. There MUST NOT be a second `[ACTION:]` executor that escapes this (today `eliza-runtime.ts processMessage` does — see HIGH).
2. **WHEN a verb/param/bound is added, removed, or changed in `npc-simulation.ts executeHatcherAction`**, the change MUST update `skill-protocol.ts` §3a (the hard-mirrored bounds `HATCHER_MOVE_MIN/MAX`, `HATCHER_TALK_MESSAGE_MAX`, `MAX_HATCHER_ACTIONS_PER_REPLY`, `HATCHER_EMOTE_MAP` keys, the 10 building ids) in the SAME diff and bump `PROTOCOL_VERSION`.
3. **WHEN a plugin `Action` is intended to be invoked via `[ACTION:]`/structured params**, its `validate()` MUST treat a present required param as the intent signal (`getParam(...)`), never rely solely on natural-language keywords in the message text — because `executeAction` passes an empty-text synthetic message (see MEDIUM).
4. **WHEN an `[ACTION:]` dispatch loop executes handlers**, it MUST enforce the documented per-reply action cap (`MAX_*_ACTIONS_PER_REPLY`, currently 4) regardless of executor, so the bound the manual advertises always holds.
5. **WHEN avatar chat, location/teacher chat, or the agent orchestrator is modified**, cognition MUST continue to run through the ElizaOS runtime (`createElizaRuntime` → `processMessage`/`useModel`); a direct LLM/API call replacing that path is a violation. Ambient NPC banter and BYO/proxy agent cognition are the ONLY sanctioned non-ElizaOS cognition surfaces and MUST be labeled as such.
6. **WHEN any game-flow/mechanic/verb/table-rule/currency/timer/weight changes**, the change MUST update all three surfaces same-diff: Nori `town-guide.ts knowledge[]` (via `CLAWVILLE_ORIENTATION_KNOWLEDGE` where canonical), the connection SKILL.md (`buildProtocolManual`), and the hosted-runtime `injectProtocolKnowledge` path (which auto-picks up a `PROTOCOL_VERSION` bump on next runtime start).
7. **WHEN classifying an agent session (hosted vs external/BYO vs pending)**, the discriminator MUST require all conjuncts of `isHostedAvatarAgentSessionRow` (platformAgentId match AND `identityType==='nanoclaw'` AND hosted harness) — a harness-or-agentId-only match is spoofable (documented Codex fix).
8. **WHEN the in-world `[ACTION:]` executor resolves a whitelist/emote/building key**, it MUST use `Object.hasOwn`/explicit resolvers (never bare bracket truthiness) so inherited prototype keys (`constructor`, `__proto__`) can never satisfy the whitelist.

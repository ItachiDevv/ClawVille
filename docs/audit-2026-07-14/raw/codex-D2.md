# codex-D2 — SECURITY: auth, agent sessions, custodial wallets, partner signing, secrets/SSRF — Forensic Audit

## Summary

The audit found **2 BLOCKER, 5 HIGH, and 1 MEDIUM** verified security defects.  
The worst issue is indefinite replay of partner-signed portal requests, allowing a captured request to mint a fresh magic-link login long after signing (`apps/api/src/routes/portal.ts:912`, `apps/api/src/services/partner-signature.ts:185`).  
Hatcher registration is also replayable within the accepted five-minute window and returns a newly minted, real-vCLAW-capable bearer on every replay (`apps/api/src/routes/partner-hatcher.ts:737`, `apps/api/src/routes/partner-hatcher.ts:806`).  
Public registration paths can overwrite or rebind an existing agent using only its caller-supplied ID, enabling ownership takeover and session invalidation (`apps/api/src/routes/agent-gateway.ts:493`, `apps/api/src/routes/openclaw.ts:218`).  
Any live agent bearer can currently be exchanged for a non-guest Lucia user cookie through the Milady exchange (`apps/api/src/routes/auth.ts:974`, `packages/database/src/schema/users.ts:171`).  
Real-economy agent bearers are embedded in request URLs, while outbound URL validation retains an acknowledged DNS-rebinding race (`apps/api/src/routes/agent-gateway.ts:975`, `apps/api/src/services/agent-substrate-client.ts:202`).  
The wallet creation primitive does enforce winner-only, one-time plaintext secret disclosure; no direct wallet `secretKey` re-emission was found in the reviewed custody implementation (`apps/api/src/services/wallet-service.ts:273`, `apps/api/src/services/wallet-service.ts:307`).

## Findings

### [BLOCKER] Replayable portal signatures can mint fresh user-login links indefinitely  —  apps/api/src/routes/portal.ts:912

- What the code does: Both `/mint-for-hatcher` and `/mint-for-scape` verify only the partner public key, signature, and raw request body, then mint and return a new session-ticket redirect (`apps/api/src/routes/portal.ts:404`, `apps/api/src/routes/portal.ts:409`, `apps/api/src/routes/portal.ts:457`, `apps/api/src/routes/portal.ts:912`, `apps/api/src/routes/portal.ts:917`, `apps/api/src/routes/portal.ts:966`). The legacy verifier checks an ed25519 signature over `sha256(rawBody)` but binds no timestamp, nonce, method, or path (`apps/api/src/services/partner-signature.ts:185`, `apps/api/src/services/partner-signature.ts:206`). Following the returned ticket creates a Lucia user session (`apps/api/src/routes/auth.ts:868`, `apps/api/src/routes/auth.ts:889`).
- Why it's wrong/risky: A previously valid signed request never expires at the signature layer. Each replay produces a distinct, currently valid login ticket, so the ticket’s own single-use and expiry controls do not prevent replay of the request that creates it (`apps/api/src/services/session-ticket-service.ts:124`, `apps/api/src/services/session-ticket-service.ts:152`).
- Failure scenario (concrete inputs -> bad outcome): An attacker captures one valid Hatcher mint request containing a target user identifier and its signature. Days later, the attacker replays the same bytes and headers to `/mint-for-hatcher`; the server creates a new ten-minute ticket and returns a new `/enter?t=...` URL. Following it creates an authenticated Lucia session for the victim (`apps/api/src/routes/portal.ts:966`, `apps/api/src/routes/portal.ts:994`, `apps/api/src/routes/auth.ts:889`).
- Fix: Replace the legacy verifier on both portal integrations with domain-separated verification covering partner ID, HTTP method, canonical path, timestamp, body hash, and a unique request nonce. Enforce the ±5-minute window and transactionally consume the nonce before minting a ticket. Retried requests must not mint another credential.

### [BLOCKER] Replaying Hatcher registration mints a fresh real-economy bearer  —  apps/api/src/routes/partner-hatcher.ts:737

- What the code does: The partner-signature policy permits identical signed write requests within the five-minute window on the assumption that all write handlers are idempotent (`apps/api/src/services/partner-signature.ts:233`, `apps/api/src/services/partner-signature.ts:242`). Hatcher registration instead generates a new `hat-` session ID for every accepted request (`apps/api/src/routes/partner-hatcher.ts:806`), overwrites the stored session hash and expiry while retaining the existing user binding (`apps/api/src/routes/partner-hatcher.ts:895`, `apps/api/src/routes/partner-hatcher.ts:911`, `apps/api/src/routes/partner-hatcher.ts:929`), marks the resulting configuration ledger-capable (`apps/api/src/routes/partner-hatcher.ts:1088`, `apps/api/src/routes/partner-hatcher.ts:1121`), and returns the plaintext bearer (`apps/api/src/routes/partner-hatcher.ts:1216`).
- Why it's wrong/risky: Credential issuance is not idempotent. A replay does not merely reproduce an existing state transition; it rotates the stored credential and discloses a new bearer authorized against the victim’s bound user and avatar.
- Failure scenario (concrete inputs -> bad outcome): An observer captures a valid signed registration request and replays it during the accepted five-minute window. The replay overwrites the victim agent’s session hash and returns the observer a new ledger-capable bearer bound to the existing user. The observer can then invoke real-vCLAW agent tools while the prior bearer fails hash validation (`apps/api/src/middleware/require-auth-or-agent.ts:145`, `apps/api/src/middleware/require-auth-or-agent.ts:167`).
- Fix: Require a unique signed partner request ID and atomically reject any successfully consumed ID. Do not mint another bearer for an exact replay. If lost-response recovery is required, use a new signed recovery exchange or an encrypted, short-lived response tied to the authenticated partner—not another bearer returned for reusable signed bytes.

### [HIGH] Caller-controlled agent IDs allow cross-owner rebinds and session takeover  —  apps/api/src/routes/agent-gateway.ts:493

- What the code does: Public `/api/agent/connect` accepts a caller-selected `agentId` and optional connection token (`apps/api/src/routes/agent-gateway.ts:205`, `apps/api/src/routes/agent-gateway.ts:262`). When the ID already exists, the route unconditionally updates its identity, gateway configuration, bearer hash, and `userId`, using the connection-token user when supplied (`apps/api/src/routes/agent-gateway.ts:493`, `apps/api/src/routes/agent-gateway.ts:506`, `apps/api/src/routes/agent-gateway.ts:516`). A non-guest authenticated user can mint a connection token that is tied to their user/avatar but not to an expected agent ID (`apps/api/src/routes/agent-gateway.ts:3645`, `apps/api/src/routes/agent-gateway.ts:3699`, `apps/api/src/routes/agent-gateway.ts:3782`). Rebinding then evicts prior sessions (`apps/api/src/routes/agent-gateway.ts:577`, `apps/api/src/routes/agent-gateway.ts:612`). The legacy unauthenticated `/api/openclaw/register` similarly updates an existing caller-selected agent ID, including its session hash and gateway (`apps/api/src/routes/openclaw.ts:123`, `apps/api/src/routes/openclaw.ts:218`, `apps/api/src/routes/openclaw.ts:248`).
- Why it's wrong/risky: Knowledge of an agent’s public ID is treated as authority to mutate or re-own that record. A connection token proves only that the caller owns some ClawVille account, not that they control the existing agent they name.
- Failure scenario (concrete inputs -> bad outcome): User B creates a valid connection token for B’s own avatar, then calls `/api/agent/connect` with User A’s agent ID. The existing row is rebound to B, its bearer is rotated, and A’s sessions are evicted. B inherits the persistent agent record and receives a live ledger-capable session. Separately, an unauthenticated caller can use the legacy register route to overwrite an existing agent’s hash and gateway, invalidating the legitimate bearer (`apps/api/src/middleware/require-auth-or-agent.ts:145`, `apps/api/src/middleware/require-auth-or-agent.ts:167`).
- Fix: Treat an existing agent binding as immutable unless the caller proves control through the current bearer, a signed agent-identity challenge, or the already-bound user’s authenticated session. Scope connection tokens to an explicit expected agent ID. Make legacy registration insert-only or remove it; it must never mutate a bound row without ownership proof.

### [HIGH] Any live agent session can be upgraded into a non-guest Lucia user account  —  apps/api/src/routes/auth.ts:974

- What the code does: `/milady-session-exchange` accepts and validates any live agent session without checking that it represents a Milady identity, an attested owner, or a ledger-capable binding (`apps/api/src/routes/auth.ts:974`, `apps/api/src/routes/auth.ts:997`). It inserts a deterministic “guest” user but omits both `isGuest` and `guestExpiresAt` (`apps/api/src/routes/auth.ts:1010`, `apps/api/src/routes/auth.ts:1024`). The database default for `isGuest` is `false` (`packages/database/src/schema/users.ts:171`). It then creates and returns a normal Lucia session cookie (`apps/api/src/routes/auth.ts:1040`). Non-guest authorization checks rely on the stored `isGuest` value (`apps/api/src/routes/agent-gateway.ts:3699`, `apps/api/src/middleware/require-auth-or-agent.ts:313`).
- Why it's wrong/risky: A bearer obtainable through a public agent connection becomes a general user-login credential. The synthetic account is described as a guest but is persisted as a normal user and therefore bypasses guest restrictions.
- Failure scenario (concrete inputs -> bad outcome): An unauthenticated caller creates a generic agent session through the public connect route, submits that bearer to `/milady-session-exchange`, and receives a Lucia cookie for a newly created non-guest user. The caller can then access flows that reject guests, including issuance of user-bound connection tokens (`apps/api/src/routes/agent-gateway.ts:3699`, `apps/api/src/routes/agent-gateway.ts:3782`).
- Fix: Require cryptographic Milady identity attestation and verify the session’s expected identity type and owner before exchange. If the route is intended to create a demo guest, atomically persist `isGuest: true`, a bounded `guestExpiresAt`, and guest-only avatar/economy semantics. An arbitrary agent bearer must never mint a full user session.

### [HIGH] Real-vCLAW bearer credentials are exposed in URL paths and query strings  —  apps/api/src/routes/agent-gateway.ts:975

- What the code does: The source identifies the agent session ID as a bearer trusted for real-vCLAW actions (`apps/api/src/routes/agent-gateway.ts:393`, `apps/api/src/routes/agent-gateway.ts:2371`). Connect responses generate URLs containing that bearer in their path (`apps/api/src/routes/agent-gateway.ts:975`, `apps/api/src/routes/agent-gateway.ts:987`) and also return the raw session ID (`apps/api/src/routes/agent-gateway.ts:1000`). Wallet access accepts `sessionId` through a query parameter (`apps/api/src/routes/agent-gateway.ts:1476`, `apps/api/src/routes/agent-gateway.ts:1491`). The real-vCLAW blackjack proxy places it directly in `/:sessionId/cove/blackjack/:tool` before forwarding it as the trusted agent-session header (`apps/api/src/routes/agent-gateway.ts:4377`, `apps/api/src/routes/agent-gateway.ts:4427`).
- Why it's wrong/risky: URL paths and queries are routinely retained in reverse-proxy/CDN access logs, browser histories, analytics, tracing systems, and copied links. Redacting authorization headers does not protect credentials embedded in the request target.
- Failure scenario (concrete inputs -> bad outcome): A production access log records a blackjack or wallet URL containing the complete session ID. Anyone with log access copies that ID and replays it against an agent tool before expiry, spending or wagering the bound avatar’s real vCLAW.
- Fix: Transport agent bearers only in `Authorization: Bearer` or `X-Clawville-Agent-Session` headers. URL paths must use non-secret agent or resource identifiers. Remove query compatibility, redact credential headers from all request logging, migrate generated skill/tool URLs, and rotate existing sessions after deployment.

### [HIGH] Outbound URL validation remains vulnerable to DNS rebinding  —  apps/api/src/services/hatcher-config.ts:247

- What the code does: Public agent setup accepts a URL-valued gateway and supports the `custom-webhook` protocol (`apps/api/src/services/agent-reconnect-session.ts:74`, `apps/api/src/services/agent-reconnect-session.ts:84`). `validateOutboundUrlResolved` resolves the hostname and checks the returned addresses, but then returns a URL that still contains the hostname (`apps/api/src/services/hatcher-config.ts:247`, `apps/api/src/services/hatcher-config.ts:263`, `apps/api/src/services/hatcher-config.ts:279`). A later independent `fetch()` performs another resolution for custom webhooks (`apps/api/src/services/agent-substrate-client.ts:738`, `apps/api/src/services/agent-substrate-client.ts:762`). The Hatcher client explicitly acknowledges this remaining validation-to-fetch DNS race (`apps/api/src/services/agent-substrate-client.ts:190`, `apps/api/src/services/agent-substrate-client.ts:202`).
- Why it's wrong/risky: The address inspected during validation is not necessarily the address used by the network connection. An attacker controlling DNS can return a public address during preflight and a private, loopback, link-local, or cloud-metadata address during the actual fetch.
- Failure scenario (concrete inputs -> bad outcome): An attacker registers `https://rebind.example` as a custom webhook. The first DNS response points to a public server and passes validation; the next response points to an internal service or metadata IP. The backend sends the webhook request to that internal target, and a compatible JSON response can relay internal content through the agent response path (`apps/api/src/services/agent-substrate-client.ts:762`, `apps/api/src/services/agent-substrate-client.ts:769`).
- Fix: Pin a validated address for the actual socket while preserving the original Host/SNI, or force all such traffic through an egress proxy/firewall that blocks private, loopback, link-local, multicast, and metadata ranges after DNS resolution. Verify the connected peer address. Manual redirect handling must remain, but it does not solve rebinding.

### [HIGH] Static shared admin cookie cannot be revoked and authorizes money-sensitive actions  —  apps/api/src/middleware/admin-only.ts:41

- What the code does: The accepted `cv_dash` cookie value is a deterministic HMAC of the fixed string `dash-access` under `FINGERPRINT_SECRET`; it contains no identity, issue time, expiry, password version, or revocation handle (`apps/api/src/middleware/admin-only.ts:41`, `apps/api/src/middleware/admin-only.ts:48`). Cookie validation occurs before the individual-user allowlist (`apps/api/src/middleware/admin-only.ts:75`). `DASH_SHARED_PASSWORD` is checked only when issuing the cookie, which is then valid for 30 days across `.clawville.world` (`apps/api/src/routes/dash-auth.ts:30`, `apps/api/src/routes/dash-auth.ts:71`, `apps/api/src/routes/dash-auth.ts:86`). Routes accepting `adminOnly` include wager settlement and enabling real-USDC partner storefronts (`apps/api/src/routes/wager.ts:586`, `apps/api/src/routes/wager.ts:615`, `apps/api/src/routes/partner-storefront.ts:353`, `apps/api/src/routes/partner-storefront.ts:390`).
- Why it's wrong/risky: Changing the shared password does not invalidate already issued cookies, despite the source comment asserting that rotation does (`apps/api/src/middleware/admin-only.ts:22`). The only effective signing-key rotation is `FINGERPRINT_SECRET`, which is shared with unrelated fingerprint functionality. The credential is also unattributable: every holder has the same value.
- Failure scenario (concrete inputs -> bad outcome): A dash cookie leaks from one operator’s browser. The operator rotates `DASH_SHARED_PASSWORD`, but the stolen cookie remains valid. During its 30-day lifetime, the attacker can select a wager winner or enable a real-money storefront without presenting an individually attributable administrator session.
- Fix: Use short-lived, server-side, revocable admin sessions tied to an authenticated administrator identity and key/password version. Require step-up authentication for settlement and real-money configuration. The shared dashboard cookie must not authorize money-moving or liability-changing routes.

### [MEDIUM] Magic-link session tickets are stored as plaintext bearer credentials  —  apps/api/src/services/session-ticket-service.ts:124

- What the code does: The ticket service generates a random plaintext ticket and stores that exact value in the database (`apps/api/src/services/session-ticket-service.ts:83`, `apps/api/src/services/session-ticket-service.ts:124`, `apps/api/src/services/session-ticket-service.ts:140`). Consumption queries by the raw value and returns the ticket-bearing record (`apps/api/src/services/session-ticket-service.ts:189`, `apps/api/src/services/session-ticket-service.ts:208`). The schema makes the raw ticket the primary key (`packages/database/src/schema/agent-session-tickets.ts:37`). In contrast, the general auth-token service hashes its raw token before storage (`apps/api/src/services/auth-token-service.ts:39`, `apps/api/src/services/auth-token-service.ts:59`).
- Why it's wrong/risky: Anyone obtaining read access to the live database, a backup, or a diagnostic export can immediately use every unconsumed ticket. The token’s single-use property does not mitigate disclosure before the legitimate user consumes it.
- Failure scenario (concrete inputs -> bad outcome): A read-only database credential is compromised while a partner login ticket is pending. The attacker copies the stored ticket, constructs `/enter?t=<ticket>`, and consumes it first, receiving a Lucia session for the target user (`apps/api/src/routes/auth.ts:868`, `apps/api/src/routes/auth.ts:889`).
- Fix: Store only a SHA-256 or keyed-HMAC digest of each ticket, return the raw ticket exactly once at issuance, and consume it by digest using an atomic expiry-and-unused predicate. Remove the plaintext ticket from persisted and returned record types, and invalidate outstanding legacy plaintext tickets during migration.

## Governing invariants

- WHEN a partner-signed request mutates state or mints any credential, the change MUST bind the partner identity, method, canonical path, timestamp, body digest, and a unique request ID into the signature; it MUST enforce ±5 minutes and atomically reject successful replays (`CLAUDE.md:226`, `apps/api/src/services/partner-signature.ts:233`).
- WHEN an operation returns or rotates an authentication bearer, the change MUST treat it as non-idempotent; an identical request MUST never mint or disclose another usable bearer (`apps/api/src/routes/partner-hatcher.ts:806`, `apps/api/src/routes/partner-hatcher.ts:1216`).
- WHEN a public route addresses an existing agent by `agentId`, the change MUST require proof from the current bearer, bound user, or cryptographically verified agent identity before changing ownership, gateway, session hash, wallet, or avatar binding (`apps/api/src/routes/agent-gateway.ts:493`, `apps/api/src/routes/openclaw.ts:218`).
- WHEN a connection token can establish a user-bound agent, the token MUST be scoped to the intended agent ID and MUST NOT authorize rebinding an agent owned by another user (`apps/api/src/routes/agent-gateway.ts:3645`, `apps/api/src/routes/agent-gateway.ts:3782`).
- WHEN a bearer authorizes custody or real-vCLAW actions, the route MUST validate its expiry and current stored hash through the central live-session validator, and the bearer MUST be transported only in an authorization header—never a path, query, log, or persistent URL (`apps/api/src/middleware/require-auth-or-agent.ts:116`, `apps/api/src/middleware/require-auth-or-agent.ts:145`).
- WHEN a route creates a guest or demonstration user, the transaction MUST explicitly set `isGuest: true`, set a bounded expiry, and bind guest-only economy semantics before issuing a cookie (`packages/database/src/schema/users.ts:171`, `apps/api/src/routes/auth.ts:1010`).
- WHEN an agent bearer is exchanged for a human user session, the change MUST verify an explicit identity attestation and ownership relationship; mere possession of a generic agent bearer MUST NOT create a Lucia user session (`apps/api/src/routes/auth.ts:974`, `apps/api/src/routes/auth.ts:1040`).
- WHEN the server sends a request to a caller- or partner-controlled URL, the actual connected destination MUST be constrained after DNS resolution through address pinning, peer-address verification, or deny-by-default egress controls; preflight lookup alone MUST NOT be considered SSRF protection (`apps/api/src/services/hatcher-config.ts:247`, `apps/api/src/services/agent-substrate-client.ts:202`).
- WHEN an admin action moves money, selects settlement, or enables real-money fulfillment, the change MUST require a short-lived, revocable, individually attributable administrator session and step-up authentication; a shared static dashboard cookie MUST NOT authorize it (`apps/api/src/routes/wager.ts:586`, `apps/api/src/routes/partner-storefront.ts:353`).
- WHEN issuing a magic-link, reconnect, password-reset, or session ticket, the change MUST store only a one-way digest and MUST atomically enforce single use and expiry (`apps/api/src/services/auth-token-service.ts:39`, `apps/api/src/services/session-ticket-service.ts:189`).
- WHEN a custodial wallet is created concurrently, only the transaction that wins first insertion MUST receive the plaintext secret; conflict losers and all subsequent reads MUST omit it (`apps/api/src/services/wallet-service.ts:273`, `apps/api/src/services/wallet-service.ts:307`).
- WHEN a private key or DEK leaves process-local plaintext form, it MUST be envelope-encrypted under the configured KEK, and no response, error, or log may contain the secret, DEK, wrapped-key plaintext, or wallet secret after first disclosure (`apps/api/src/services/keypair-vault.ts:206`, `apps/api/src/services/keypair-vault.ts:306`).
- WHEN `ALLOW_TEST_PARTNER_PUBKEY` is enabled, module initialization MUST fail unless `CLAWVILLE_ENV` is explicitly staging; production MUST never silently accept the test key (`apps/api/src/services/partner-signature.ts:96`, `CLAUDE.md:299`).

## Doc drift

- `CLAUDE.md` requires partner writes to be ed25519-verified with a ±5-minute window (`CLAUDE.md:226`), but both portal mint integrations use a legacy signature verifier with no timestamp or freshness input (`apps/api/src/routes/portal.ts:409`, `apps/api/src/routes/portal.ts:917`, `apps/api/src/services/partner-signature.ts:185`). `ARCHITECTURE.md` describes these portal mint paths without documenting this exception (`ARCHITECTURE.md:516`, `ARCHITECTURE.md:520`).
- `ARCHITECTURE.md` and the partner integration specification state that partner writes are replay-safe/idempotent (`ARCHITECTURE.md:518`, `docs/hatcher-integration-spec.md:74`), but registration creates and returns a new bearer on every accepted request (`apps/api/src/routes/partner-hatcher.ts:806`, `apps/api/src/routes/partner-hatcher.ts:1216`).
- `ARCHITECTURE.md` characterizes the partner outbound surface as SSRF-guarded (`ARCHITECTURE.md:520`), while the implementation explicitly records a residual DNS validation-to-fetch race (`apps/api/src/services/agent-substrate-client.ts:202`).
- `ARCHITECTURE.md` describes `cv_dash` as a shared-password fallback (`ARCHITECTURE.md:208`) but does not document that the deterministic cookie can authorize wager settlement and real-money storefront configuration or that password rotation cannot revoke it (`apps/api/src/middleware/admin-only.ts:48`, `apps/api/src/routes/wager.ts:586`, `apps/api/src/routes/partner-storefront.ts:353`).
- The Milady exchange labels its synthetic identity as a guest in source, but omits the database flags that define a guest (`apps/api/src/routes/auth.ts:1010`, `packages/database/src/schema/users.ts:171`). Canonical architecture documentation lists the exchange but does not specify or warn about this privilege-bearing behavior (`ARCHITECTURE.md:316`).

## Coverage note

This review covered the listed auth/session, portal identity, custody, partner-signature, Hatcher configuration, outbound cognition, namespace, admin middleware, session-ticket, reconnect-schema, wager, storefront, and relevant database-schema paths. It was a static read-only audit: no partner harness, runtime tests, DNS-rebinding test, database query, deployed-environment inspection, or network request was executed. Production values for `CLAWVILLE_ENV`, partner keys, proxy/CDN URL redaction, egress firewalling, and Cloudflare Worker deployment are therefore **UNVERIFIED**. The test-partner-key guard appears crash-loud by static inspection (`apps/api/src/services/partner-signature.ts:96`), but its deployed configuration is **UNVERIFIED**. Downstream authorization on every route using `requireAuthOrAgentSession`, the complete Covenant/Scape partner implementation, Solana transaction signing internals, and operational access controls for logs/backups were not exhaustively audited.

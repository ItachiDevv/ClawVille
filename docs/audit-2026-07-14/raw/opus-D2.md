# opus-D2 — SECURITY (auth, agent sessions, custodial wallets, partner signing, secrets/SSRF) — Forensic Audit

## Summary
The D2 security surface is, overall, in strong shape and shows the scar tissue of many prior adversarial rounds: ed25519 partner verification is over exact raw bytes, agent-session liveness routes through ONE fail-closed gate (`validateLiveAgentSession`) that enforces DB TTL + bearer-hash rotation, custodial keys use envelope encryption with a KEK held off-box, `secretKey` is disclosed exactly-once with race-loser suppression, and every outbound cognition/webhook/launch path is DNS-aware SSRF-guarded with `redirect:'manual'`. Crash-loud env guards (`FINGERPRINT_SECRET`, `ALLOW_TEST_PARTNER_PUBKEY`/`CLAWVILLE_ENV`) throw at module load as documented. The worst issue found is a **replay-window inconsistency**: the `/api/portal/mint-for-*` and `/accept-*-link` reverse-portal routes verify with the WINDOWLESS `verifyPartnerSignature` (no timestamp, no nonce), while the equally-sensitive partner-hatcher write path was explicitly upgraded to a ±5-min windowed verifier — and these portal routes MINT LOGIN TICKETS, so a captured signed request is replayable forever into a fresh account-takeover magic link. Headline: 1 HIGH, 3 MEDIUM, 2 LOW. No BLOCKER found.

## Findings

### [HIGH] Reverse-portal partner routes use the windowless verifier — captured signed request replayable forever into a victim-login ticket — `apps/api/src/routes/portal.ts:409,501,917,1011`
- What the code does: `mint-for-scape`, `accept-scape-link`, `mint-for-hatcher`, `accept-hatcher-link` authenticate with `verifyPartnerSignature('<partner>', {pubkeyHeader, signatureHeader, rawBody})` (`partner-signature.ts:185`). That function verifies ed25519 over `sha256(rawBody)` against the `PARTNER_PUBKEYS` allowlist but reads **no timestamp header and enforces no freshness window or nonce**. `mint-for-hatcher` (`portal.ts:912`) then mints a magic-link session ticket via `mintSessionTicket({userId, …})` and returns `redirectUrl` = a `/enter?t=<sess-…>` login link that logs the browser in AS `userId` (the `principal:clawville:<uuid>` from the signed body).
- Why it's wrong/risky: the project's OWN standard for partner writes is a timestamp + ±5-min window — `verifyPartnerWriteSignature` (`partner-signature.ts:311`, used by `partner-hatcher.ts:440`) was deliberately introduced precisely because "idempotency alone does not bound how LONG a captured request stays valid" (SEC-2, `partner-signature.ts:226-249`). These portal routes are MORE sensitive than the hatcher agent-register writes that got the window (they mint account-takeover login tickets, not a body-less agent upsert) yet were left on the legacy windowless verifier. `hatcher` is a LIVE configured partner, so `mint-for-hatcher`/`accept-hatcher-link` are live and windowless in prod.
- Failure scenario: an attacker who captures ONE signed `mint-for-hatcher` request (partner-side log leak, TLS-terminating proxy, a compromised/curious intermediary, or a partner incident) can replay the exact bytes + `X-Hatcher-Issuer-Pubkey`/`X-Hatcher-Signature` headers indefinitely. Each replay returns a fresh valid 10-min login ticket for the victim ClawVille `userId` → the attacker clicks `/enter?t=…` and is authenticated as the victim, with real-CT/economy access. A window would cap the capture's usefulness to 5 minutes; today it never expires.
- Fix: migrate all four reverse-portal routes to a windowed, domain-separated, method+path+timestamp+body-hash-bound verifier (reuse `verifyPartnerWriteSignature`, adding an `X-<Partner>-Timestamp` header to the partner contract), OR add a partner-supplied nonce consumed delete-on-read (mirror `consumeNonce` in `auth-challenge.ts`) gated on durable success. Bump the partner CONTRACT/spec + `PROTOCOL_VERSION` since the wire changes. At minimum, add a timestamp + ±5-min window to `verifyPartnerSignature` and require it here.

### [MEDIUM] Milady session-exchange mints a full NON-guest account from an agent bearer — the "milady guest" is not flagged `is_guest` — `apps/api/src/routes/auth.ts:1010-1034`
- What the code does: `POST /api/auth/milady-session-exchange` validates the agent session (correctly, via `validateLiveAgentSession`, `auth.ts:1004`) then find-or-creates a user with `email = milady-<agentId>@clawville.guest` and inserts `{id, email, passwordHash, name}` — it does **NOT** set `isGuest: true` (contrast `auth.ts:1256` guest path which sets `isGuest`, `guestExpiresAt`). The comment (`auth.ts:806`) calls the result a "milady guest" user.
- Why it's wrong/risky: the guest→real-CT backstop in `resolveAgentSession` (`require-auth-or-agent.ts:330-338`) forces a session non-ledger ONLY when `users.isGuest` is true. A milady-exchange user is `isGuest=false`, so an agent bound to it is treated as a real, ledger-capable owner and the demo-economy guard never fires — despite the code/comment framing it as a "guest". This is either an unintended economy-parity gap (a runtime-trusted Milady agent silently gets real economy under a "guest" label) or an undocumented intentional decision; the code and its own comments disagree.
- Failure scenario: a Milady plugin caller drives `milady-session-exchange` → obtains a Lucia cookie for a `*.clawville.guest`-emailed, non-guest account → participates in the REAL CT economy/leaderboard, bypassing the demo restriction every other guest path enforces.
- Fix: decide explicitly. If Milady exchange is meant to be demo, set `isGuest: true` (+ `guestExpiresAt`) on the insert so the ledger backstop binds. If it is meant to be a first-class real account (Milady is a first-class harness), stop calling it a "guest", drop the `.clawville.guest` email suffix from the security narrative, and document that these are real economy participants.

### [MEDIUM] `mint-for-scape`/`mint-for-hatcher` have no per-partner rate limit or idempotency on a login-ticket mint — `apps/api/src/routes/portal.ts:404,912`
- What the code does: both reverse-portal mint routes go straight from signature-verify to `mintSessionTicket` with no `createRateLimiter`/`getClientIp` throttle and no idempotency key (unlike `partner-hatcher.ts:738-741` which rate-limits, and `wallet-withdraw.ts:152` which requires an Idempotency-Key).
- Why it's wrong/risky: combined with the HIGH replay gap, an attacker (or a buggy partner) can mint unbounded valid login tickets for a principal in a tight loop; even absent replay, a compromised partner key can enumerate/mint at will. Ticket rows accumulate unbounded and each is a live credential within its TTL.
- Failure scenario: a loop of replayed/valid `mint-for-hatcher` calls floods `agent_session_tickets` with live victim-login tickets and creates a wide window for one to be clicked.
- Fix: add the shared per-IP (interim) rate limiter used elsewhere, and consider binding a partner-supplied request id as an idempotency key so a replay/retry returns the same (single) ticket rather than minting new ones. Rolls up naturally with the HIGH fix.

### [MEDIUM] Local hosted-runtime cognition (`hermes-local`/`openclaw-local`) is intentionally SSRF-unchecked — safe today, fragile to a future refactor — `apps/api/src/services/agent-substrate-client.ts:368,459,560`
- What the code does: `chatHermesLocal`/`chatOpenclawLocal`/`prewarmLocalGateway` POST to `HERMES_LOCAL_GATEWAY_URL`/`OPENCLAW_LOCAL_GATEWAY_URL` with **no `validateOutboundUrlResolved` guard**, by design (documented `agent-substrate-client.ts:352-362,443-452`) because the target is a compile-time constant an SSRF guard would only veto.
- Why it's wrong/risky: the safety invariant is "these URLs are constants no caller/row can influence." That is true today (`agent-session-config.ts` derives them from env constants), but the guarantee is a comment, not a mechanism — if a future change ever lets a bot row or caller field flow into these gateway URLs, the loopback POST (carrying the local bearer) becomes an SSRF with no guard. The `resolveInWorldProtocol` gate that routes to these paths is the only thing standing between a caller-influenced URL and an unguarded fetch.
- Failure scenario: a refactor that sources the local gateway URL from `config.gatewayUrl` (as the openai/anthropic paths do) would silently reintroduce blind SSRF on the localhost bearer path.
- Fix: keep the constants literally inlined at the fetch call (not passed through config), or add an assertion that `gatewayUrl === HERMES_LOCAL_GATEWAY_URL` (constant identity) before the unguarded POST, so a future indirection fails loudly rather than opening SSRF.

### [LOW] Envelope-encryption Worker unwrap trusts the plaintext DEK length only — no AAD binding of DEK↔row — `apps/api/src/services/keypair-vault.ts:296-321`
- What the code does: `decryptSecretKeyEnveloped` unwraps `dekWrapped` via the CF Worker, checks `dek.length === 32`, then AES-GCM-decrypts. The wrapped DEK is not bound (AAD) to the row/subject it belongs to.
- Why it's wrong/risky: AES-GCM auth-tag already prevents cross-row DEK swaps from decrypting (a mismatched DEK fails the tag), so this is defense-in-depth, not an exploit. But a swapped/wrapped-DEK from another row would surface as a generic decrypt error rather than an explicit "this DEK is not for this row" signal, and there is no cryptographic binding proving the unwrapped DEK belongs to `row.id`.
- Failure scenario: operational — a mis-paired `(encryptedSecretKey, dekWrapped)` after a bad migration decrypts to garbage/throws with no clear provenance, complicating incident response on custodial keys.
- Fix: bind the row id (or `subject_type:subject_id`) as AES-GCM AAD on encrypt/decrypt, and/or include it in the Worker wrap context, so an unwrapped DEK is cryptographically pinned to its row.

### [LOW] `X-CV-Fingerprint` is fully client-controlled — a farm can rotate it to get fresh anti-farm buckets — `apps/api/src/middleware/fingerprint.ts:82,105-109`
- What the code does: tier-1 `fpInput` is the raw browser-supplied `X-CV-Fingerprint` header, salted+hashed server-side. The `(fp_hash, ip_prefix_hash)` pair is the anti-farm cap key.
- Why it's wrong/risky: the `fp_hash` half is attacker-chosen (any non-empty header value yields a distinct bucket). The `ip_prefix_hash` half still collapses a single /24, so a single-VPS farm is capped — but a farm distributed across many /24s that also rotates the fingerprint header gets fully fresh budgets. This is an accepted-by-design tradeoff (the header is the "preferred" signal) but it is worth flagging: the fingerprint contributes little adversarial value on its own.
- Failure scenario: distributed farm rotates `X-CV-Fingerprint` + spreads across IP prefixes → per-subject daily caps (chat/collab/building) are multiplied by the number of prefixes.
- Fix: treat `fp_hash` as advisory only for anti-farm scoring (it already is secondary to `ip_prefix_hash`); ensure the economically-meaningful caps that matter (real-CT paths) are anchored on server-derived identity (userId/avatar) not the fingerprint — which they are for the ledger, so this is mostly a leaderboard-farming note.

## Governing invariants (enforceable rules that should bind every future change)
- WHEN any partner-authenticated route MUTATES state or mints a credential/ticket, the change MUST verify with a domain-separated signature bound to method+path+timestamp+body-hash AND enforce a ±5-min freshness window (or a delete-on-read nonce gated on durable success) — the windowless `verifyPartnerSignature` MUST NOT gate a state-mutating or ticket-minting route.
- WHEN a route mints a Lucia session / magic-link ticket from a partner or agent credential, the change MUST rate-limit per partner/IP and SHOULD bind an idempotency key so a replay/retry cannot fan out into multiple live login credentials.
- WHEN any code path resolves a subject to `ledgerCapable`/real-CT, the change MUST keep `users.isGuest` as the single source of truth AND MUST NOT create an economy-participating account without an explicit, documented guest/non-guest decision (no "guest"-named row that is silently non-guest).
- WHEN an outbound fetch targets a URL, the change MUST either (a) DNS-aware SSRF-validate a caller/row-influenced URL on EVERY send with `redirect:'manual'`, or (b) fetch a compile-time constant inlined at the call site — a caller/row value MUST NEVER reach an unguarded fetch.
- WHEN a custodial secret is disclosed, it MUST be emitted exactly once on first creation (`firstTimeSecretKeyBase58`/`isFirstTime`), never re-emitted, never logged; the race-loser MUST NOT receive the secret.
- WHEN a staging-only affordance (`ALLOW_TEST_PARTNER_PUBKEY`) or a hard-required secret (`FINGERPRINT_SECRET`) is added, the guard MUST throw at MODULE LOAD (crash-loud) on the forbidden env, never silently degrade.
- WHEN a public/unsigned registration path takes a caller-supplied `agentId`/`identityType`, it MUST reject reserved partner namespaces up front (`isReservedPartnerAgentId`) AND refuse to mutate a row whose `identity_type` is reserved (`isReservedPartnerIdentityType`).
- WHEN an agent-session bearer is trusted anywhere, resolution MUST route through `validateLiveAgentSession` (Map + DB `session_expires_at > now`, NULL = expired, present-and-mismatched `session_key_hash` = torn down) — Map membership alone MUST NEVER authorize a bearer.

## Doc drift (canonical doc vs live code)
- CLAUDE.md "PROTECTED SURFACE" lists `routes/portal.ts (incl. mint-for-hatcher / accept-hatcher-link)` and mandates contract-locked signing, but those routes use the windowless `verifyPartnerSignature` while the doc's security-invariant bullet ("partner writes ed25519-verified + ±5 min windowed") is satisfied only by the partner-hatcher write path — the portal reverse-portal routes silently violate the stated ±5-min-window invariant. Reconcile the code (add the window) and the spec (`docs/hatcher-integration-spec.md`).
- `auth.ts:806` comment ("authenticated as a 'milady guest' user") vs `auth.ts:1024` code (no `isGuest`) — doc/comment says guest, live code creates a non-guest. Fix code or comment per the MEDIUM finding.
- ARCHITECTURE.md §7 custody narrative should note the envelope-DEK is length-checked but not AAD-bound to its row (LOW finding) so the threat model is stated precisely.

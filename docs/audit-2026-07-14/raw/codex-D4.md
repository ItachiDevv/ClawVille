# codex-D4 — Agent Runtime, ElizaOS, Protocol Parity — Forensic Audit
## Summary
The core wrapper genuinely instantiates and initializes ElizaOS `AgentRuntime`; it is not a direct-API replacement (`packages/agent-runtime/src/eliza-runtime.ts:503`, `packages/agent-runtime/src/eliza-runtime.ts:529`, `packages/agent-runtime/src/eliza-runtime.ts:563`).
No BLOCKER was verified, but the hosted-agent protocol-knowledge path is behaviorally disconnected from both retrieval and autonomous decisions.
The autonomous driver remains a teaching-building loop rather than the promised full-scope economic participant.
Baccarat, cash Hold’em, and slots accept real agent-session settlement, but their playable contracts are absent from the connection manual.
Hosted-session classification can be shadowed by a dead BYO row, causing the frontend to treat a live hosted agent as disconnected.
Headline count: 0 BLOCKER, 4 HIGH, 2 MEDIUM, 2 LOW.
The requested autonomy audit document is absent from this checkout, so its conclusions could not be cross-checked.

## Findings
### [HIGH] Injected protocol knowledge is write-only for hosted agents  —  packages/agent-runtime/src/eliza-runtime.ts:882
- What the code does: The orchestrator injects the current manual into hosted avatar/house runtimes (`apps/api/src/services/agent-orchestrator.ts:225`, `apps/api/src/services/agent-orchestrator.ts:232`). The injector deliberately stores it under a generated `protocol-knowledge` room and entity (`packages/agent-runtime/src/eliza-runtime.ts:914`, `packages/agent-runtime/src/eliza-runtime.ts:915`, `packages/agent-runtime/src/eliza-runtime.ts:916`, `packages/agent-runtime/src/eliza-runtime.ts:942`). The only general knowledge provider instead searches with `roomId` and `entityId` equal to the avatar/platform-agent identifier (`packages/agent-runtime/src/providers/knowledge.ts:42`, `packages/agent-runtime/src/providers/knowledge.ts:43`, `packages/agent-runtime/src/providers/knowledge.ts:48`, `packages/agent-runtime/src/providers/knowledge.ts:49`). The injector itself admits that only a “future protocol-aware reader” could query its isolated room (`packages/agent-runtime/src/eliza-runtime.ts:883`, `packages/agent-runtime/src/eliza-runtime.ts:885`).
- Why it's wrong/risky: Surface three of the three-surface sync rule exists only as persisted rows; no live provider retrieves those rows. Autonomous decisions bypass `processMessage` and all providers entirely by calling raw `useModel` (`packages/agent-runtime/src/eliza-runtime.ts:1418`, `packages/agent-runtime/src/eliza-runtime.ts:1427`).
- Failure scenario (concrete inputs -> bad outcome): `PROTOCOL_VERSION` adds a new economy tool and the hosted runtime successfully writes its section. The agent’s next autonomous decision still receives neither that section nor any other protocol-memory row, so it cannot discover or apply the new contract.
- Fix: Add a protocol-knowledge provider that queries the exact generated room/entity and selects only the highest complete version, then include it in autonomous decision composition. Add an integration test that injects a unique protocol fact and proves both hosted chat and `decide()` receive it.

### [HIGH] “Autonomous” ignores full-scope directives and can only visit teachers  —  apps/api/src/services/agent-autonomy-driver.ts:802
- What the code does: The driver’s decision prompt always presents teaching buildings, asks the model to choose one teacher, and mandates exactly one `enter_building` tag (`apps/api/src/services/agent-autonomy-driver.ts:809`, `apps/api/src/services/agent-autonomy-driver.ts:836`, `apps/api/src/services/agent-autonomy-driver.ts:841`, `apps/api/src/services/agent-autonomy-driver.ts:846`, `apps/api/src/services/agent-autonomy-driver.ts:848`). Its phase machine then only walks, conducts a teacher conversation, and returns to deciding (`apps/api/src/services/agent-autonomy-driver.ts:619`, `apps/api/src/services/agent-autonomy-driver.ts:650`, `apps/api/src/services/agent-autonomy-driver.ts:658`, `apps/api/src/services/agent-autonomy-driver.ts:716`).
- Why it's wrong/risky: Nori tells users that directives such as “grind vCLAW in the cove” and “run my shop” become the agent’s top-priority goal (`packages/agent-templates/src/locations/town-guide.ts:269`). The manual likewise invites those directives (`apps/api/src/services/skill-protocol.ts:742`, `apps/api/src/services/skill-protocol.ts:761`). In practice, `formatDirectiveContext` can only bias which teacher is selected (`apps/api/src/services/agent-autonomy-driver.ts:833`, `apps/api/src/services/agent-autonomy-driver.ts:838`).
- Failure scenario (concrete inputs -> bad outcome): A human sets `grind vCLAW in the cove`. The driver injects that text, then requires the model to select a teaching building and emit `enter_building`; it cannot emit `enter_cove`, open a game session, wager, or settle.
- Fix: Replace the teacher-only planner with a goal/action state machine covering the documented authenticated tools, including server-held session use, idempotent economy actions, controlled-mode suppression, and durable progress. Until then, narrow Nori/manual copy to “choose and visit teachers.”

### [HIGH] Three live Cove agent paths are missing from the connection protocol  —  apps/api/src/services/skill-protocol.ts:581
- What the code does: Baccarat, cash Hold’em, and slots all resolve `X-Clawville-Agent-Session` to a ledger-capable bound avatar (`apps/api/src/routes/cove-baccarat.ts:269`, `apps/api/src/routes/cove-baccarat.ts:279`, `apps/api/src/routes/cove-baccarat.ts:288`; `apps/api/src/routes/cove-holdem.ts:293`, `apps/api/src/routes/cove-holdem.ts:303`, `apps/api/src/routes/cove-holdem.ts:312`; `apps/api/src/routes/cove-slots.ts:327`, `apps/api/src/routes/cove-slots.ts:338`, `apps/api/src/routes/cove-slots.ts:352`). Their live write endpoints include baccarat open/coup/close (`apps/api/src/routes/cove-baccarat.ts:468`, `apps/api/src/routes/cove-baccarat.ts:634`, `apps/api/src/routes/cove-baccarat.ts:1120`), Hold’em open/deal/action/close (`apps/api/src/routes/cove-holdem.ts:688`, `apps/api/src/routes/cove-holdem.ts:855`, `apps/api/src/routes/cove-holdem.ts:1058`, `apps/api/src/routes/cove-holdem.ts:1666`), and slots open/spin/close (`apps/api/src/routes/cove-slots.ts:545`, `apps/api/src/routes/cove-slots.ts:893`, `apps/api/src/routes/cove-slots.ts:1569`). The manual provides playable sections only for blackjack and tournament poker (`apps/api/src/services/skill-protocol.ts:581`, `apps/api/src/services/skill-protocol.ts:646`); the other games appear only as replay event names (`apps/api/src/services/skill-protocol.ts:338`, `apps/api/src/services/skill-protocol.ts:339`, `apps/api/src/services/skill-protocol.ts:340`).
- Why it's wrong/risky: A raw route accepting an agent header is not a fully reachable agent feature when the connection contract never teaches the agent the endpoints, payloads, idempotency requirements, or state machine. Nori also still says Hold’em and baccarat autonomy are future work (`packages/agent-templates/src/locations/town-guide.ts:174`, `packages/agent-templates/src/locations/town-guide.ts:212`).
- Failure scenario (concrete inputs -> bad outcome): A connected agent fetches protocol v18 and wants to play baccarat. It learns that baccarat settlements may appear in replay, but receives no open/coup/close instructions, so it cannot originate the supposedly parity-complete play flow.
- Fix: Publish session-bound tool bundles or complete REST contracts for all three games, update Nori and hosted protocol delivery in the same diff, and bump `PROTOCOL_VERSION`. Add contract tests asserting every agent-capable game router has a discoverable manual/tool entry.

### [HIGH] A dead BYO row shadows a live hosted agent classification  —  apps/api/src/routes/auth.ts:119
- What the code does: `/me/agent-session` selects the user’s most recently seen bot row without first selecting the hosted avatar’s own row (`apps/api/src/routes/auth.ts:125`, `apps/api/src/routes/auth.ts:126`, `apps/api/src/routes/auth.ts:127`). Any bot row that does not exactly match the hosted internal-session discriminator is classified as external expired, idle, or active before the no-bot hosted branch can run (`apps/api/src/services/agent-session-classify.ts:120`, `apps/api/src/services/agent-session-classify.ts:138`, `apps/api/src/services/agent-session-classify.ts:152`, `apps/api/src/services/agent-session-classify.ts:167`, `apps/api/src/services/agent-session-classify.ts:195`).
- Why it's wrong/risky: The hosted ElizaOS avatar remains alive, but a stale BYO credential makes the authoritative API report `connected:false`. The frontend then clears its paired/connected state (`apps/web/src/app/game/page.tsx:393`, `apps/web/src/app/game/page.tsx:402`) and fails the hosted-mode check that suppresses the meaningless reconnect flow (`apps/web/src/components/game/avatar-chat-bar.tsx:69`, `apps/web/src/components/game/avatar-chat-bar.tsx:81`).
- Failure scenario (concrete inputs -> bad outcome): A hosted-Hermes account temporarily connects a BYO agent. Five minutes after that process stops, its row becomes `external-idle`; `/me/agent-session` returns disconnected even though the account’s hosted avatar runtime still exists, hiding Autonomous controls and showing reconnect behavior.
- Fix: Resolve hosted-avatar liveness independently from external rows. Represent both states if both matter, or fall back to `mode:'hosted'` when the selected external row is idle/expired. Query active avatar and hosted internal row explicitly rather than using an unconstrained latest-row precedence rule.

- Why it's wrong/risky: A proxy that embeds or extracts only the explicitly authoritative whitelist section concludes the sixth verb is unavailable. - Failure scenario (concrete inputs -> bad outcome): A Hatcher client generates its allowed-action schema from §3a. It never exposes `enter_poker_room`, despite the server accepting it and the poker section requiring it.
- Fix: Define one machine-readable action descriptor shared by executor validation and manual rendering. Add a set-equality test for verb and parameter parity, render `enter_poker_room` in §3a, and bump the protocol version.

### [MEDIUM] Protocol promises poker skill accumulation that does not exist  —  apps/api/src/services/skill-protocol.ts:713
- What the code does: The tournament section states that each hand accrues poker skill into agent memory (`apps/api/src/services/skill-protocol.ts:713`, `apps/api/src/services/skill-protocol.ts:714`). The game-skill service explicitly supports only blackjack and labels baccarat, Hold’em, and slots as future work (`apps/api/src/services/game-skill-memory.ts:41`, `apps/api/src/services/game-skill-memory.ts:42`); its only writer is `recordBlackjackSkillMemory` (`apps/api/src/services/game-skill-memory.ts:103`). Nori separately records hosted per-hand memory as still TODO (`packages/agent-templates/src/locations/town-guide.ts:168`, `packages/agent-templates/src/locations/town-guide.ts:169`).
- Why it's wrong/risky: This is direct three-surface contradiction and overstates the ElizaOS learning loop. Tournament agents receive no persistent poker edge despite being told that improvement is part of the play contract.
- Failure scenario (concrete inputs -> bad outcome): An agent plays ten tournament hands, reconnects, and expects prior-hand lessons to inform later decisions. No poker game-skill rows are written or read; its next decision has no accumulated poker memory.
- Fix: Implement idempotent post-hand poker memory writes and pre-decision retrieval, or remove the promise from the manual and Nori until implemented. Either contract change requires a protocol bump.

## Governing invariants
- WHEN protocol knowledge is injected into an ElizaOS runtime, the change MUST provide and test a live retrieval path from both chat and autonomous decision generation; persisted-but-unread memory does not satisfy three-surface sync.
- WHEN a hosted agent makes an autonomous decision, the change MUST compose through ElizaOS providers/memory or explicitly inject equivalent current protocol context; raw `useModel` calls MUST NOT silently bypass required world knowledge.
- WHEN a directive names an economy or gameplay goal, the autonomous planner MUST either execute the documented authenticated tool flow or return a typed unsupported-goal state; it MUST NOT reinterpret every goal as “choose a teacher.”
- WHEN any human economy/game route accepts an agent session, the same diff MUST publish a discoverable agent contract or tool bundle, update Nori, update hosted-runtime knowledge, and bump `PROTOCOL_VERSION`.
- WHEN the executor whitelist changes, one machine-readable descriptor MUST drive both validation and manual rendering, with tests asserting exact verb, parameter, enum, bound, and normalization equality.
- WHEN a hosted account also has BYO session rows, classification MUST resolve hosted-runtime liveness independently and MUST NOT let an idle/expired external credential erase a live hosted agent.
- WHEN protocol memory is versioned, readers MUST select the newest complete version and writers MUST record completeness; a partially embedded version MUST NOT become authoritative silently.
- WHEN a manual claims learn-through-play, the settle path MUST write idempotent game-skill memory and the decision path MUST read it before the claim ships.
- WHEN an agent body idle-despawns, authenticated activity MUST restore the body without changing economic identity or downgrading ledger capability; session TTL and body lifetime MUST remain separate.
- WHEN token terminology is rendered to a human or conversational agent, copy MUST use `$CLAWVILLE`; `vCLAW` and legacy `ct` identifiers MUST remain confined to internal/wire contexts.

# codex-D1 — ECONOMY & MONEY-PATHS — Forensic Audit
## Summary
- Overall health is mixed: the EARNED redemption rail uses exact integer fee math and capture-before-send delivery, but older and cross-rail paths do not consistently meet that standard (`apps/api/src/services/earned-redemption.ts:112`, `apps/api/src/services/earned-redemption.ts:1260`).
- Headline count: **4 BLOCKER, 3 HIGH, 2 MEDIUM**.
- Worst issue: x402 transaction-signature uniqueness is scoped separately to each table, allowing one payment proof to bind to both a top-up and generic checkout (`packages/database/src/schema/land.ts:685`, `packages/database/src/schema/checkout.ts:140`).
- Canonical vCLAW balances are directly mutated outside the ledger by the item guest path and operator scripts (`apps/api/src/routes/items.ts:143`, `packages/database/scripts/grant-test-tokens.ts:50`).
- Real-value wager routes and the tutorial reward claim violate mandatory connected-agent parity (`apps/api/src/routes/wager.ts:197`, `apps/api/src/routes/quests.ts:1401`).
- Wager broadcasts lack durable pre-send intent/signature capture and can leave on-chain state disconnected from the database (`apps/api/src/routes/wager.ts:294`, `apps/api/src/routes/wager.ts:478`).
- The production x402 configuration accepts arbitrary facilitator URLs and credits based solely on that server’s response, without independent chain verification (`apps/api/src/services/x402-config.ts:154`, `apps/api/src/services/x402-payai.ts:496`).

## Findings
### [BLOCKER] x402 payment signatures are unique per table, not globally  —  packages/database/src/schema/land.ts:641
- What the code does: Top-ups protect `tx_signature` only inside `ct_topups`, while generic purchases independently protect it only inside `x402_checkouts` (`packages/database/src/schema/land.ts:685`, `packages/database/src/schema/checkout.ts:140`). Both rails derive the same payment requirement fields—scheme, network, amount, asset, merchant `payTo`, timeout, and fee payer—from `buildTopupQuote`; the resource URL is outside the accepted requirement (`apps/api/src/services/x402-payai.ts:213`, `apps/api/src/services/x402-payai.ts:231`). Generic checkout calls that same builder with the merchant wallet and USD-cent price (`apps/api/src/services/x402-checkout.ts:284`).
- Why it's wrong/risky: The top-up schema explicitly states that PayAI supplies no idempotency and the database must enforce it, but the enforcement stops at a table boundary (`packages/database/src/schema/land.ts:641`). No constraint prevents the same Solana signature appearing once in each table.
- Failure scenario (concrete inputs -> bad outcome): Create a 300-vCLAW generic checkout and a $3.00 top-up. They produce equivalent payment requirements at the same merchant, network, and fee payer. Submit the same signed payment payload to both settle machines. If the facilitator returns the already-landed signature on the second submission, each table accepts it and independently credits/fulfills value (`apps/api/src/routes/ct-topup.ts:400`, `apps/api/src/services/x402-checkout.ts:498`). Live PayAI’s exact duplicate-response behavior was not exercised in this read-only audit and is **UNVERIFIED**, but the database structurally permits the duplicate binding.
- Fix: Add a global `x402_settlement_receipts` table keyed by `tx_signature`, with recipient, mint, atomic amount, network, consumer type, and consumer ID. Every normal-settle and reconciliation path must claim that row transactionally before credit or fulfillment. Existing per-table indexes should remain as defense in depth.

### [BLOCKER] Canonical avatar balances are mutated outside the ledger  —  apps/api/src/routes/items.ts:143
- What the code does: The guest item path row-locks an avatar and directly updates `clawTokens` and `softBalance`, deliberately writing no ledger transaction (`apps/api/src/routes/items.ts:92`, `apps/api/src/routes/items.ts:138`). `grant-test-tokens.ts` loads the ordinary `.env.local` database, defaults to granting 5,000 units to a fixed avatar, executes raw balance SQL, and has no production/staging guard (`packages/database/scripts/grant-test-tokens.ts:16`, `packages/database/scripts/grant-test-tokens.ts:23`, `packages/database/scripts/grant-test-tokens.ts:50`). The staging-account seeder also directly resets balances, although it is protected by a staging-project check (`apps/api/scripts/seed-test-accounts.ts:39`, `apps/api/scripts/seed-test-accounts.ts:134`).
- Why it's wrong/risky: The ledger declares itself the mandatory path for every `avatars.clawTokens` write and atomically maintains balance, provenance, transaction, and covenant records (`apps/api/src/services/claw-token-ledger.ts:4`, `apps/api/src/services/claw-token-ledger.ts:13`). Raw writes make the canonical avatar balance disagree with ledger reconstruction and bypass covenant attribution.
- Failure scenario (concrete inputs -> bad outcome): Run `grant-test-tokens.ts` with an `.env.local` pointing at production and no arguments. It grants the hard-coded avatar 5,000 SOFT vCLAW without passing the earned-mint or normal credit chokepoints (`packages/database/scripts/grant-test-tokens.ts:7`, `packages/database/scripts/grant-test-tokens.ts:23`). Separately, every guest book purchase changes the canonical avatar balance with no corresponding transaction record (`apps/api/src/routes/items.ts:140`).
- Fix: Store demo currency in a separate guest/session wallet that can never become a real ledger balance. Convert all scripts to the canonical ledger API, require an explicit staging database identity for test grants, and remove every raw `avatars.claw_tokens` update outside migrations.

### [BLOCKER] SOL wager economy writes are human-only  —  apps/api/src/routes/wager.ts:197
- What the code does: Create, join, cancel, and refund use `requireAuth` plus `requireNonGuestUser`, read `c.get('user')`, and resolve a human-owned avatar (`apps/api/src/routes/wager.ts:197`, `apps/api/src/routes/wager.ts:214`, `apps/api/src/routes/wager.ts:450`, `apps/api/src/routes/wager.ts:686`, `apps/api/src/routes/wager.ts:778`).
- Why it's wrong/risky: These routes deposit, escrow, or refund SOL, yet connected/hosted agents cannot invoke them as their bound avatar. The mechanical E5 rule calls any economy path gated only by `requireAuth` an automatic blocking defect (`CLAUDE.md:34`, `CLAUDE.md:41`).
- Failure scenario (concrete inputs -> bad outcome): A ledger-capable connected agent sends `X-Clawville-Agent-Session` to create or join a wager lobby. The route never resolves that session and rejects it before the agent can deposit or later claim its refund, while the equivalent Lucia-cookie human succeeds (`apps/api/src/routes/wager.ts:197`, `apps/api/src/routes/wager.ts:450`).
- Fix: Use `requireAuthOrAgentSession`, `requireLedgerCapableIdentity`, and `requireNonGuestIdentity`; bind every ownership/deposit record to `identity.avatarId`, retain the bound owner user only where required by existing foreign keys, and stamp agent attribution. Expose the same operation through the agent tool/action surface.

### [BLOCKER] Tutorial quest rewards are human-only  —  apps/api/src/routes/quests.ts:1401
- What the code does: Normal quest acceptance, start, and submission support `requireAuthOrAgentSession`, but tutorial claiming switches back to `requireAuth`, resolves a Lucia user avatar, and keys the claim by `user.id` (`apps/api/src/routes/quests.ts:694`, `apps/api/src/routes/quests.ts:809`, `apps/api/src/routes/quests.ts:853`, `apps/api/src/routes/quests.ts:1401`, `apps/api/src/routes/quests.ts:1444`). It then credits that avatar through the ledger (`apps/api/src/routes/quests.ts:1490`).
- Why it's wrong/risky: This is a state-changing vCLAW mint that a connected agent cannot reach as itself, violating E5’s mandatory quest/economy parity (`CLAUDE.md:34`, `CLAUDE.md:41`).
- Failure scenario (concrete inputs -> bad outcome): A connected agent completes verifiable tutorial activity and submits the claim with its live bearer. The human-only middleware rejects it; the same bound avatar can claim only after its owner repeats the request with a Lucia cookie.
- Fix: Resolve the canonical identity with the same middleware as the other quest routes. Key idempotency on the bound avatar/quest or a documented cross-surface subject key so the human and its connected agent cannot claim the same reward twice.

### [HIGH] Wager broadcasts are not durable across chain/DB ambiguity  —  apps/api/src/routes/wager.ts:294
- What the code does: Lobby creation inserts a draft, invokes Anchor `.rpc()`, then deletes the draft on any thrown error (`apps/api/src/routes/wager.ts:273`, `apps/api/src/routes/wager.ts:294`, `apps/api/src/routes/wager.ts:303`, `apps/api/src/services/wager-program-client.ts:365`). Join broadcasts first and only afterward inserts the player and increments the lobby in two separate statements (`apps/api/src/routes/wager.ts:478`, `apps/api/src/routes/wager.ts:489`, `apps/api/src/routes/wager.ts:498`). Settle, cancel, and refund repeat the chain-first/database-second pattern (`apps/api/src/routes/wager.ts:643`, `apps/api/src/routes/wager.ts:653`, `apps/api/src/routes/wager.ts:742`, `apps/api/src/routes/wager.ts:752`, `apps/api/src/routes/wager.ts:820`, `apps/api/src/routes/wager.ts:830`).
- Why it's wrong/risky: `.rpc()` combines send and confirmation; a timeout can occur after the transaction landed. The wrapper labels transport failures but stores no pre-send intent or captured signature capable of distinguishing “not sent” from “landed” (`apps/api/src/services/wager-program-client.ts:256`, `apps/api/src/services/wager-program-client.ts:268`). This contradicts the schema’s declaration that on-chain state is authoritative for money while off-chain rows power discovery and refunds (`packages/database/src/schema/wager.ts:24`, `packages/database/src/schema/wager.ts:159`).
- Failure scenario (concrete inputs -> bad outcome): `joinSolLobby` lands the deposit, then the process dies before `lobby_players` insertion. The player’s PDA and SOL exist on-chain, but `/refund` returns `not_in_lobby` because it requires the missing database row (`apps/api/src/routes/wager.ts:792`, `apps/api/src/routes/wager.ts:798`). During creation, a post-send timeout causes the route to delete the only discovery row even if the on-chain lobby exists.
- Fix: Persist a durable intent and deterministic PDA before broadcast; build/sign explicitly, capture the signature before sending, and transition with guarded states such as `prepared → sending → confirmed/reconcile`. Never delete or reset an ambiguous transaction. Add a chain reconciliation worker that repairs off-chain lobby/player state from PDAs.

### [HIGH] The documented wager devnet/mainnet gate does not exist  —  apps/api/src/services/wager-program-client.ts:84
- What the code does: The route says the program is devnet-only, that routes never sign mainnet RPC URLs, and references a `SOLANA_RPC_URL` guard (`apps/api/src/routes/wager.ts:35`, `apps/api/src/routes/wager.ts:42`). The client instead constructs its connection from any `SOLANA_RPC_URL`, imports no cluster constant, and performs no genesis-hash check (`apps/api/src/services/wager-program-client.ts:59`, `apps/api/src/services/wager-program-client.ts:84`). The package’s nominal cluster constant is devnet/localnet-only, but the service does not import it (`packages/wager-program/src/index.ts:47`, `packages/wager-program/src/index.ts:53`).
- Why it's wrong/risky: A single environment mistake silently removes the asserted devnet safety boundary. The settlement authority can also be overridden by environment, so the default devnet key comparison is not a mainnet interlock (`apps/api/src/services/wager-program-client.ts:146`).
- Failure scenario (concrete inputs -> bad outcome): Set `SOLANA_RPC_URL` to a mainnet endpoint and set the authority override to the stored key. The service boots and attempts signed wager instructions on mainnet. If the program is unavailable, production wagering breaks; if the program is deployed there, real SOL moves despite the feature gate.
- Fix: Require an explicit wager cluster, verify the RPC genesis hash at startup, and pin the expected program/config/authority for that cluster. Production must crash loudly unless a separately reviewed mainnet code gate is enabled.

### [HIGH] An arbitrary x402 facilitator can fabricate successful payments  —  apps/api/src/services/x402-config.ts:154
- What the code does: Any non-empty `X402_FACILITATOR_URL` overrides known presets without protocol or host validation (`apps/api/src/services/x402-config.ts:154`, `apps/api/src/services/x402-config.ts:159`). The production boot guard checks only whether the preset or mock flag says `mock`, not the resolved URL (`apps/api/src/services/x402-config.ts:87`). `verifyAndSettle` trusts the configured server and declares settlement complete when it returns `isValid:true`, `success:true`, and any non-empty transaction string (`apps/api/src/services/x402-payai.ts:452`, `apps/api/src/services/x402-payai.ts:482`, `apps/api/src/services/x402-payai.ts:496`, `apps/api/src/services/x402-payai.ts:513`). The top-up path then credits BOUGHT vCLAW without independently proving that transaction on-chain (`apps/api/src/routes/ct-topup.ts:603`, `apps/api/src/routes/ct-topup.ts:627`).
- Why it's wrong/risky: The crash-loud mock restriction can be bypassed simply by leaving the preset as `cdp` and setting an explicit URL to a rubber-stamping service. The returned string is treated as money proof.
- Failure scenario (concrete inputs -> bad outcome): Production has a merchant pubkey and `X402_FACILITATOR_URL=https://fake.example`, while `X402_FACILITATOR_PRESET` remains unset. The fake service returns valid/success with `transaction:"anything"`. The route captures that string and mints BOUGHT vCLAW although no USDC moved.
- Fix: Permit only exact, HTTPS, credential-free facilitator origins on production; require a staging-only override for custom endpoints. Before any credit or fulfillment, independently fetch and validate the transaction’s success, recipient ATA, USDC mint, atomic amount, payer where applicable, and network.

### [MEDIUM] Activity rewards have no durable replay barrier  —  packages/database/src/schema/activity-results.ts:36
- What the code does: `issueRewardsForRoom` inserts an `activity_results` row and credits vCLAW every time it is called (`apps/api/src/services/activity/reward-pipeline.ts:360`, `apps/api/src/services/activity/reward-pipeline.ts:457`, `apps/api/src/services/activity/reward-pipeline.ts:482`). Although the schema describes one row per participant per match, it defines only non-unique leaderboard indexes and no unique `(room_id, avatar_id)` constraint (`packages/database/src/schema/activity-results.ts:15`, `packages/database/src/schema/activity-results.ts:92`).
- Why it's wrong/risky: Idempotency exists only in the in-memory FSM’s expected call sequence, not at the economic write boundary. A worker retry, duplicate process, compensation script, or future recovery path can mint the same match reward again.
- Failure scenario (concrete inputs -> bad outcome): Invoke `issueRewardsForRoom` twice with the same room and `simResults`. Both transactions insert new result rows and both call `creditClawTokens`, deterministically paying every eligible participant twice.
- Fix: Add a unique `(room_id, avatar_id)` constraint or a unique room-settlement claim. Insert/claim first and credit only when that claim is newly created; a conflict must return the stored result without another ledger credit.

### [MEDIUM] Wager payout/rake reporting is derived from mutable DB state and a hard-coded rate  —  apps/api/src/services/wager-program-client.ts:594
- What the code does: After on-chain settlement, the API calculates the reported pot using off-chain `joinedCount` and calculates rake with a literal `500n`. It does not store or decode the on-chain rake snapshot (`apps/api/src/services/wager-program-client.ts:594`, `apps/api/src/services/wager-program-client.ts:599`, `apps/api/src/services/wager-program-client.ts:600`, `apps/api/src/services/wager-program-client.ts:611`). The code’s own remediation deadline was 2026-07-01 (`apps/api/src/services/wager-program-client.ts:608`).
- Why it's wrong/risky: On-chain settlement remains authoritative, but the response, event log, and analytics can report a different payout if the config rate rotates or off-chain joined count drifts.
- Failure scenario (concrete inputs -> bad outcome): Rotate on-chain rake from 500 to 444 bps, or lose one post-chain join update. Settlement pays the chain-correct amount, while the API reports a 5% rake calculated from the wrong participant count (`apps/api/src/routes/wager.ts:671`).
- Fix: Decode the confirmed settlement event/account values and report those. At minimum, persist immutable `rake_bps_snapshot` and reconciled participant count when the lobby is created/locked.

## Governing invariants
- WHEN any x402-backed rail accepts a settlement, the change MUST atomically claim the transaction signature in one global, cross-rail receipt registry before minting, fulfilling, releasing goods, or marking success (`packages/database/src/schema/land.ts:641`, `packages/database/src/schema/checkout.ts:139`).
- WHEN any service may broadcast SOL, USDC, or $CLAWVILLE, the change MUST persist the signed transaction signature and exact intent before broadcast; every post-capture ambiguity MUST enter forward-only reconciliation and MUST NOT delete, reset, re-sign, or resend (`apps/api/src/services/earned-redemption.ts:1260`, `apps/api/src/services/earned-redemption.ts:1267`).
- WHEN a route mutates economy or durable player state, the change MUST resolve both Lucia humans and ledger-capable connected agents to the bound avatar, reject guests where no demo tier exists, and expose an agent-callable surface (`CLAUDE.md:34`, `CLAUDE.md:41`).
- WHEN vCLAW changes, the change MUST use the canonical ledger inside the same transaction as the business-state transition; demo balances MUST live outside canonical avatar balance columns (`apps/api/src/services/claw-token-ledger.ts:4`, `apps/api/src/services/claw-token-ledger.ts:13`).
- WHEN a reward or settlement can be retried, the change MUST claim a durable unique economic-event key before crediting, and only the successful first claim may mutate value (`apps/api/src/services/activity/reward-pipeline.ts:457`, `packages/database/src/schema/activity-results.ts:92`).
- WHEN production selects an RPC or facilitator, the change MUST validate the exact cluster/genesis, protocol, host, program, recipient, and authority at boot and crash loudly on mismatch (`apps/api/src/services/wager-program-client.ts:84`, `apps/api/src/services/x402-config.ts:154`).
- WHEN reporting payout, rake, escrow, or refund values, the change MUST use confirmed on-chain evidence or immutable creation-time snapshots, never mutable discovery state or a hard-coded current rate (`packages/database/src/schema/wager.ts:24`, `apps/api/src/services/wager-program-client.ts:599`).
- WHEN generating a custodial wallet, the change MUST expose its plaintext secret only from the successful first insert; race losers and existing-wallet paths MUST return public data only (`apps/api/src/services/wallet-service.ts:258`, `apps/api/src/services/wallet-service.ts:285`, `apps/api/src/services/wallet-service.ts:318`).

# opus-D1 — ECONOMY & MONEY-PATHS — Forensic Audit

## Summary
Overall health of the crown-jewel money paths is **high**. The canonical ledger (`claw-token-ledger.ts`), the CLV buy-leg swap guard (`clv-swap-live.ts`), the EARNED redemption exit rail (`earned-redemption.ts`), the on-ramp (`ct-topup.ts` / `x402-checkout.ts`), and the withdraw executor are all production-grade: row-locked atomic mutations, capture-before-send, claim-first, reconcile-on-ambiguous, on-chain delivery verification, and a genuinely-enforced EARNED chokepoint (type + runtime capability-token + test). Exit-rail math is exact (1 vCLAW = 10,000 µUSD = $0.01; 444 µUSD exit fee = 444 bps; 9,556 µUSD buy; 444+9,556 = 10,000 — verified conserving). I found **no BLOCKER** (no cashable-money faucet, no double-spend of custody, no settle-twice on the real-money rails).

The worst issues are a step down from that: (1) baccarat **over-mints** the banker commission to the house treasury on every banker win — a real vCLAW supply-conservation break (house-ward, non-cashable SOFT, invisible to the faucet monitor); (2) `xp-service.awardXp` is a **non-atomic read-modify-write** that double-credits the level-up token under concurrency; (3) the **wager** real-SOL lobby has **no connected-agent parity** (E5 structural violation) and a **falsely-documented** mainnet guard. Headline count: **BLOCKER 0 · HIGH 3 · MEDIUM 4 · LOW 5.**

## Findings

### [HIGH] Baccarat over-mints the banker commission to the house treasury (supply-conservation break) — apps/api/src/routes/cove-baccarat.ts:856, 881-901
- **What the code does:** On a WON banker bet it credits the player the FULL engine payout `Number(r.payout)` (line 856-869), then ALSO credits the house treasury `Number(r.commission)` on top (881-895). The engine's `r.payout` for a banker win already embodies the 0.95:1 rate (`stake + floor(stake*95/100)`) and `r.commission = stake - floor(stake*95/100)` (confirmed by the in-file comment 871-880 and `cove-verify-compat.ts` banker settle).
- **Why it's wrong/risky:** Blackjack (`cove-blackjack.ts:1864/1892`) and hold'em (`cove-holdem.ts:1389/1454`) CARVE the rake OUT of the player payout — player gets `payout − rake`, treasury gets `rake`, sum = `payout`, so supply is unchanged vs the burn model. Baccarat does NOT reduce the player payout (the vig is already in the 0.95 rate), so crediting the treasury the commission on top **mints new vCLAW from nothing**: on a banker win, `player_net (+floor(0.95·stake)) + treasury (+commission)` inflates total supply. It flips a correctly-deflationary game (≈1.06% house edge) into a **net-inflationary** one, and the mint is invisible to the dedicated faucet detector (`cove-economy.ts` sums `cove_game_events` / `payout` only; the commission lands in `claw_token_transactions` only — the T0 "nothing double-counts" note at `cove-economy.ts:22-27` is true for blackjack/hold'em but FALSE for baccarat). Mitigating: the mint is house-ward (no player profits) and lands in a non-cashable SOFT house sink, so it is not a direct cashable-money loss — hence HIGH, not BLOCKER.
- **Failure scenario:** 1,000 banker bets of stake 100. Players correctly net-lose ~1,130 CT (the real edge). But the treasury is ALSO minted `commission (≈5) × ~507 wins ≈ 2,535 CT` from nothing, unfunded by any debit or payout reduction — total vCLAW supply inflates, the treasury balance overstates true house revenue >2×, and the faucet monitor stays green.
- **Fix:** Remove the treasury commission credit (881-901). The vig is already realized in the reduced 0.95 payout + the implicit burn; there is no separate pot to move. Do NOT instead reduce the player payout by the commission (that would pay ~0.90 and break the RTP). If a spendable treasury balance equal to the edge is genuinely wanted, mint the NET edge via aggregate accounting, not a per-coup gross-commission credit.

### [HIGH] xp-service.awardXp double-credits the level-up token under concurrency (non-atomic read-modify-write) — apps/api/src/services/xp-service.ts:31-76
- **What the code does:** Reads `{xp, level, totalXp}` with a plain `db.query.avatars.findFirst` (no `FOR UPDATE`, no transaction, 31-34), computes level-ups in JS (46-50), writes the new XP/level with a bare `db.update(avatars)` (56-64), then in a **separate, un-shared** `creditClawTokens` call mints `TOKENS_PER_LEVEL_UP (50)` per level gained (67-76). Called fire-and-forget from NPC chat (`routes/chat.ts` `awardXp(avatar.id, 5, 'npc-chat')`).
- **Why it's wrong/risky:** The read→compute→credit sequence holds no row lock and shares no transaction, so two concurrent `awardXp` calls for the same avatar both observe the same pre-level-up state, both decide a level-up occurred, and both `creditClawTokens(50)`. There is no idempotency key or per-level claim row to collapse the duplicate → the level-up token is minted twice (and one `+5` XP is lost — a classic lost update). The minted balance is SOFT (source `system`), so not directly cashable, but it is still an uncapped-under-concurrency mint into a player-controlled balance.
- **Failure scenario:** Avatar at `xp=97, level=1` (`XP_PER_LEVEL(1)=100`). Client fires two NPC-chat POSTs in the same tick → two `awardXp(+5)`. Both read `xp=97`, both compute `102 ≥ 100` → level 2, `tokensAwarded=50`. Both credits commit → **100 vCLAW minted for one legitimate level-up.** Repeatable at every level boundary.
- **Fix:** Wrap the whole operation in `db.transaction`, `SELECT … FOR UPDATE` the avatar row inside it, compute level-ups off the locked row, and pass that same `tx` into `creditClawTokens` so the XP advance and the mint commit atomically. This also closes the partial-failure value-loss (level write commits, credit throws → token never payable — see LOW below).

### [HIGH] Wager real-SOL lobby has NO connected-agent parity (E5 violation) — apps/api/src/routes/wager.ts:197, 450, 686, 778
- **What the code does:** Every write route — create (`:197`), join (`:450`), cancel (`:686`), refund (`:778`) — is gated `requireAuth, requireNonGuestUser` and resolves the actor via `loadAvatarForUser(user.id)` reading `c.get('user')` (Lucia only). There is NO `requireAuthOrAgentSession` / `X-Clawville-Agent-Session` / `resolveAgentSession` path anywhere in the file (confirmed: `import { … requireAuth }` at `:63`, `requireNonGuestUser` at `:64`, no agent import).
- **Why it's wrong/risky:** Wagers escrow **real SOL** on-chain (`joinSolLobby`/`settleSolLobby`) — an economy feature under Rule E5, which mandates that a connected/hosted agent play AS ITSELF with real settlement + leaderboard credit. Every other real-money surface here resolves an agent (`ct-topup`, `x402-checkout`, `wallet-withdraw`, `exchange`, all four cove games). Wager is human-XOR-nothing — a connected agent is structurally locked out of a money-handling feature, the exact violation E5 was written to forbid (the Cove precedent). (Currently devnet-gated by `FEATURE_GATE: wager-mainnet-paid`, which lowers blast radius but not the structural defect.)
- **Failure scenario:** A hosted agent with a bound avatar + funded custodial wallet tries to join a SOL wager lobby → `requireAuth` 401s it (no Lucia cookie). The agent can never create/join/settle/refund or earn `activity.match.placed` leaderboard credit, while a human can.
- **Fix:** Swap `requireAuth`/`requireNonGuestUser` → `requireAuthOrAgentSession`/`requireNonGuestIdentity`; resolve the avatar from `identity.avatarId` (as `exchange.ts:79`); gate the on-chain deposit to a ledger/ownership-proven agent session; add a PARITY note; expose the wager verbs on the agent action surface + protocol SKILL.md with a `PROTOCOL_VERSION` bump.

### [MEDIUM] Wager mainnet network guard is documented but does NOT exist — apps/api/src/services/wager-program-client.ts:84-88
- **What the code does:** `RPC_URL = process.env.SOLANA_RPC_URL ?? 'https://api.devnet.solana.com'` and a single module-scope `Connection(RPC_URL)` (88) drives every create/join/lock/settle/cancel/refund. There is **no assertion that the endpoint is devnet.**
- **Why it's wrong/risky:** The route-level `FEATURE_GATE: wager-mainnet-paid` (`wager.ts:35-42`) claims the program is "devnet-only; routes never sign mainnet RPC URLs" and points at *"this file's SOLANA_RPC_URL guard"* — but no such guard exists in either file. Contrast the withdraw executor's real `assertMainnetWithdrawConnection` (`wallet-withdraw-executor.ts:158`). Precedence rule = code wins; the code has no protection, so the documented safety control is fictitious.
- **Failure scenario:** An operator sets `SOLANA_RPC_URL` to a mainnet endpoint (or it's inherited from a sibling service's env) → the client builds+signs+sends settlement txs against mainnet with the custodial keypairs + settlement authority, with nothing in code to stop it. (Blast radius limited only by the devnet `PROGRAM_ID` likely being absent on mainnet — luck, not a guard.)
- **Fix:** Add a devnet assertion (inverse of `assertMainnetWithdrawConnection`) that throws before any `.rpc()` unless the endpoint is unambiguously devnet, OR gate mainnet behind an explicit reviewed `CLAWVILLE_ENV`-style signal. Until then, correct the FEATURE_GATE text so it does not assert a control that isn't there.

### [MEDIUM] Activity/reef-race reward issuance has no persistent idempotency — double-credit prevented only by in-memory FSM state — apps/api/src/services/activity/reward-pipeline.ts:361-505 + activity-room-manager.ts:968
- **What the code does:** `issueRewardsForRoom` inserts one `activity_results` row per participant and `creditClawTokens` each non-bot/non-guest in one tx (457-505), invoked once from the `live→results` FSM transition. Re-issuance is blocked ONLY because `VALID_TRANSITIONS.results = {gc}` and the room object is process-local in-memory.
- **Why it's wrong/risky:** There is no DB-level guard against paying a room twice — no `rewards_issued` flag on `activity_rooms`, no `UNIQUE(room_id, avatar_id)` on `activity_results`. Any path that re-drives a room to `results` (crash-recovery re-adoption, manual re-trigger, a second manager instance) would re-insert results and re-credit the placement base tokens with zero DB resistance (PB/first-play bonuses self-suppress on replay, but base placement does not).
- **Failure scenario:** Room settles, credits 40 vCLAW to the winner; a crash-recovery/duplicate-manager path calls `transitionRoom(roomId,'results')` again → second `activity_results` row + second 40 vCLAW credit, nothing to reject it.
- **Fix:** Add a persistent barrier independent of in-memory state — a `UNIQUE(room_id, avatar_id)` on `activity_results` (second insert 23505s, rolling back before the credit) or a `rewards_issued_at` CAS on `activity_rooms` checked inside the reward tx.

### [MEDIUM] Hold'em house edge lives entirely in bot AI; 5-CT rake cap can't reclaim a beatable-bot faucet — apps/api/src/routes/cove-holdem.ts:136, 1374, 1454
- **What the code does:** 1 human/agent seat + 5 house bots each funded a VIRTUAL `BOT_STACK = 100n` reset every hand (never bought in, never ledgered). Chips won from bots become real CT at cash-out. The only house take is `computeHoldemRake` = 5% of pot capped at **5 CT/hand** (correctly carved + conserving at the ledger, 1389/1454).
- **Why it's wrong/risky:** The settlement conserves, but the house EDGE is not in the settlement — it is entirely in the bot decision quality (`holdem-engine.ts`, outside my read scope). A human/agent can win up to ~500 CT of MINTED real vCLAW from the virtual bot stacks in a single all-in hand while the rake on that hand is capped at 5 CT. If the bots are exploitable (deterministic/weak/seed-replayable), the table is a net faucet: real CT minted from virtual bot chips faster than the 5-CT/hand rake reclaims — the exact "never let a game be a CT faucet" concern.
- **Failure scenario:** An agent playing near-GTO (or exploiting deterministic bot behavior) nets >5 CT/hand from the bots → sustained real-CT-positive against the house, conservation-clean at the ledger.
- **Fix:** Not resolvable in the route. Requires an EV audit of `holdem-engine.ts` bot AI for a provable house edge (or an uncapped/raised rake) before any real-money tier. Flagged for engine-level audit.

## Findings — LOW

### [LOW] Bounty cancel-refund downgrades provenance EARNED/BOUGHT → SOFT — apps/api/src/routes/bounties.ts:2660-2666
- On CT-rail bounty cancel, the refund `creditClawTokens(bounty.tokenReward)` mints SOFT (default provenance), but creation debited the creator burning SOFT→BOUGHT→EARNED. A creator who escrowed BOUGHT/EARNED CT gets it back as non-cashable SOFT — they lose their own cashability. House-favorable (not a faucet), same laundering-defense pattern as `transferClawTokens`, but a silent user-value downgrade. Fix: if bounty escrow must preserve cashability, snapshot the burned tags at debit and restore them on refund; otherwise document the downgrade in the bounty UI.

### [LOW] Wager on-chain deposit and off-chain rows are not atomic — orphan deposit + refund lockout — apps/api/src/routes/wager.ts:478-502, 308-323
- `join`/`create` do the on-chain deposit, then a separate `db.insert(lobbyPlayers)` + `joinedCount` bump with no wrapping tx. If the chain deposit lands but the insert crashes, SOL is escrowed with no `lobby_players` row, and the refund route (`:792`) requires that row → the depositor is locked out of route-level refund (recoverable only by direct on-chain refund). Fix: record a durable `pending-join` intent before the chain call and reconcile from chain state, or fall the refund back to on-chain Player-PDA existence.

### [LOW] Wager settle/refund DB writes lack a status CAS — apps/api/src/routes/wager.ts:598-663, 802-838
- `settle`/`refund` read state, call chain, then update unconditionally (no `WHERE state='locked'` / atomic `refunded=true` flip before the chain call). Conservation is safe only because on-chain state rejection serializes double-settle and settle is `adminOnly` — fragile if the auth surface widens. Fix: gate the DB update with a status CAS + `.returning()`, treating 0 rows as the idempotent replay (matching exchange/ct-topup discipline).

### [LOW] Blackjack floor-based rake rounds to 0 for net profit < 20 CT — apps/api/src/routes/cove-blackjack.ts (computeBlackjackRake)
- `rake = floor(max(0, net) · 5/100)` → any winning hand netting < 20 CT pays zero rake. Bounded (<1 CT/hand) and the base dealer-rule edge still applies, so not a faucet on its own; slightly thins the intended 5% edge on small pots. Fix (optional): 1-CT minimum rake on any positive net, or round-half-up.

### [LOW] items.ts guest purchase is the one raw `avatars.clawTokens` write outside the ledger — apps/api/src/routes/items.ts:143-146
- The guest book-buy does a row-locked `UPDATE avatars SET clawTokens=…, softBalance=…` with NO `claw_token_transactions` row. This is **accepted**: it is guest-demo-only (guaranteed soft-only, `FOR UPDATE`-locked, decrements `claw_tokens` + `soft_balance` together so the `avatars_vclaw_balance_sum` CHECK holds, no house-treasury credit). Documented at 100-146. Noted only so future audits don't mistake it for a real-economy write; keep it guest-gated forever.

## Governing invariants (enforceable rules for this subsystem)
- **WHEN any code mutates `avatars.clawTokens` / a per-tag balance column, the change MUST** route through `claw-token-ledger` (`creditClawTokens`/`debitClawTokens`/`transferClawTokens`/`mintEarned`/`debitEarnedForRedemption`) inside a transaction with the avatar row `FOR UPDATE`-locked. The ONLY permitted raw write is a guest-demo, soft-only, CHECK-safe, no-ledger-row branch (items.ts pattern) that never touches the real economy.
- **WHEN a provably-fair game credits a win, the change MUST** keep the game net-neutral-or-negative to total vCLAW supply: the rake/vig is either carved OUT of the player payout (player gets `payout − rake`, treasury gets `rake`, sum = `payout`) OR realized implicitly in the payout rate — NEVER both. Crediting a treasury fee ON TOP of an already-vig-reduced payout is a supply mint and is forbidden.
- **WHEN a reward/level/quest/activity path credits vCLAW, the change MUST** be idempotent at the DB layer (row `FOR UPDATE` + status CAS, or a UNIQUE claim row, or a per-(subject,day) cap `UPDATE … WHERE under-cap RETURNING`) — never guarded only by in-memory state or an unlocked read-modify-write.
- **WHEN a path mutates economy state (games, wagers, shops, exchange, quests, wallets), the change MUST** resolve BOTH a logged-in human AND a connected/hosted agent (`requireAuthOrAgentSession` + `resolveAgentSession` → bound avatar → real ledger), keep guests demo/read-only server-side, and carry a PARITY note. `requireAuth`-only / user-XOR-guest on an economy write is a BLOCKING E5 defect.
- **WHEN a money path signs an on-chain transaction, the change MUST** assert its network (devnet/mainnet) in CODE before signing — a documented-but-absent network guard is treated as no guard (code wins).
- **WHEN an on-chain deposit/escrow is taken, the change MUST** make the off-chain durable row and the chain call recoverable together (durable pending-intent before the chain call + chain-state reconciliation), so a crash between them never strands funds or locks the depositor out of refund.
- **WHEN EARNED is minted, the change MUST** go through `mintEarned` only (type + runtime `EARNED_TOKEN` capability + test enforce it); a `backed` declaration MUST carry exact house custody (`amount·10,000` µUSDC in the `earned-backing` treasury wallet), and only a verified, vested, non-clawed, external-payer backed lot may enter the E3 exit rail.

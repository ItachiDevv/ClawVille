## NEW FINDINGS (severity-ranked)

### F1 — HIGH — `agent-pay` is an in-game vCLAW faucet via Sybil self-payment (no conservation on the mint)

`payAgent` moves REAL USDC on-chain from the sender's custodial wallet **directly to the recipient's custodial wallet** (`payTo: row.recipientWallet`, [agent-pay.ts:514](../../apps/api/src/services/agent-pay.ts#L514); comment [agent-pay.ts:286-289](../../apps/api/src/services/agent-pay.ts#L286)) and then **mints EARNED vCLAW to the recipient equal to the full USD value** (`mintEarned … backing: { kind: 'none' }`, [agent-pay.ts:290-308](../../apps/api/src/services/agent-pay.ts#L290)). `usdToCt` is a 1:1 $0.01-peg ([x402-payai.ts:122-130](../../apps/api/src/services/x402-payai.ts#L122)). **The sender's in-game balance is never debited** — the entire service has no `debit`/`mint` on the sender side; the recipient simply gains spendable vCLAW that did not exist before.

Because the payer's on-chain gas is **sponsored by the PayAI facilitator** (the fee-payer co-signer, [x402-payai.ts:167-175](../../apps/api/src/services/x402-payai.ts#L167); passed into `prepare({ feePayer })` [agent-pay.ts:509-515](../../apps/api/src/services/agent-pay.ts#L509)), the sender parts with **only the USDC principal — which lands in a wallet the same actor controls in the Sybil case.**

**Exploit:** an attacker provisions two non-guest, avatar-bound, ledger-capable accounts A and B (two email signups each auto-provision an avatar + custodial wallet), funds A with a small USDC float, then:
1. A pays B $X → B mints `X*100` spendable EARNED vCLAW; the USDC now sits in B's wallet.
2. B pays A $X → A mints `X*100` spendable EARNED vCLAW; the USDC returns to A's wallet.
3. Repeat. The USDC ping-pongs between two attacker wallets (net-zero principal, facilitator-sponsored gas) while **each hop mints the full dollar value as fresh in-game vCLAW from nothing.**

The only guard is `self_pay_forbidden`, which blocks same-avatar/same-wallet only ([agent-pay.ts:645-655](../../apps/api/src/services/agent-pay.ts#L645)); it cannot detect same-beneficial-owner. Recipient eligibility is just "distinct, non-guest, avatar-bound" ([agent-pay.ts:173-193](../../apps/api/src/services/agent-pay.ts#L173)). Bounds are weak: per-payment max defaults to **$10** (`AGENT_PAY_MAX_USD_CENTS`, [agent-pay.ts:45-50](../../apps/api/src/services/agent-pay.ts#L45)), and **there is NO per-subject/day cap and NO route-level rate limit** — the route middleware is only `sessionMiddleware + requireAuthOrAgentSession + requireNonGuestIdentity` ([routes/agent-pay.ts:65-72](../../apps/api/src/routes/agent-pay.ts#L65)). Reachable by any connected/external agent AND any human with two accounts; memory notes agent↔agent payout is LIVE on prod.

**Severity bound (honest):** the minted EARNED is `backing:'none'`, so it can **never** enter the E3 cash-out rail — `debitEarnedForRedemption`/`consumeEarnedLots` only accept `backing_kind='backed' AND payer_verification='verified'` lots ([claw-token-ledger.ts:462-493](../../apps/api/src/services/claw-token-ledger.ts#L462), [:818-859](../../apps/api/src/services/claw-token-ledger.ts#L818)). So this is **NOT real-dollar theft** — the redemption barrier holds. The damage is **in-game spendable-supply inflation**: unlimited vCLAW to dominate the leaderboard, buy out land/cosmetics, and bankroll the Cove indefinitely — a direct violation of the repo's "NEVER a vCLAW faucet" / conservation rule for the in-game economy. It also silently inflates each avatar's EARNED balance for a griefer targeting a victim's `agentId`.

**Fix direction:** treat unbacked agent-pay as a per-subject metered privilege — add a per-sender and per-recipient daily USD cap + a route rate limit; and/or do not mint spendable vCLAW for an unbacked transfer at all (record it as a non-spendable receipt), or require the dollar to route through `purpose='earned-backing'` house custody before any spendable mint (the "future cashable ④" the code comment already anticipates, [agent-pay.ts:286-289](../../apps/api/src/services/agent-pay.ts#L286)).

### F2 — LOW/INFO — concrete money impact of the known double-drive hole is bounded (answering hunt item 4)

The prior audits flagged that external REST + cove tool traffic bypasses the `humanControlled` lease. **Traced for actual money damage:** a human and a connected/external agent on the same avatar resolve to the **same `userId`**, so cove sessions are the SAME row (keyed on `userId`, [cove-slots.ts:391-404](../../apps/api/src/routes/cove-slots.ts#L391)), settlement serializes on the shoe/session `FOR UPDATE` lock, and rate limits share one `u:${userId}` bucket ([cove-slots.ts:381-389](../../apps/api/src/routes/cove-slots.ts#L381)). Consequently double-drive can **race two actors onto one shared bankroll/hand but cannot double-spend, over-credit, or drive a negative balance** — the ledger row-lock + status-CAS guards hold. Impact is confusing concurrency, not a conservation break. (No fix required for money integrity; still a UX/fairness defect owned by the connect-flow finding.)

### F3 — INFO / follow-up — activities reward pipeline is a designed uncapped-per-day SOFT faucet worth a cap check

The reward pipeline is a designed credit-only faucet (`creditClawTokens … reason:'activity_match_placed'`, [reward-pipeline.ts:515-538](../../apps/api/src/services/activity/reward-pipeline.ts#L515)); it is exactly-once per room (`activityResults` `onConflictDoNothing` on `(roomId, avatarId)` is the durable claim, [reward-pipeline.ts:503-511](../../apps/api/src/services/activity/reward-pipeline.ts#L503)) and correctly excludes bots (`if (!isBot && tokensAwarded > 0)`). The leaderboard daily cap (10 `activity.match.placed`/day) governs **scoring**, not the CT credit. I did not find a per-day cap on the CT *credit* itself; whether a real agent queueing many matches/day can farm SOFT vCLAW beyond intent is worth an explicit confirmation (lower magnitude than F1; SOFT and non-cashable).

## CHECKED AND CLEAN (verified bank-grade; not re-flagging)

- **Ledger primitive** (`claw-token-ledger.ts`): every mutation `SELECT … FOR UPDATE` row-locks the avatar, writes total + 3 tag columns in one UPDATE, inserts the ledger row + covenant record in the same tx; sum-invariant enforced by a PG CHECK. EARNED chokepoint is type-level + runtime-token + test enforced ([:317-321](../../apps/api/src/services/claw-token-ledger.ts#L317)). `transferClawTokens` always credits receiver SOFT (laundering defense). Solid.
- **Cove slots** — `Idempotency-Key` required; `(sessionId, idempotencyKey)` unique index trips inside the txn (23505 → rollback); session `FOR UPDATE` with engine-recompute-under-lock ([cove-slots.ts:1093-1266](../../apps/api/src/routes/cove-slots.ts#L1093)). Cache-miss race closed by the unique index.

- **Cove baccarat** — same FOR UPDATE + 23505 + `status='settled'` guards ([cove-baccarat.ts:507-909](../../apps/api/src/routes/cove-baccarat.ts#L507)).
- **agent-pay idempotency/settlement machine** — `(senderAvatarId, idempotencyKey)` unique; `claimPending` status-CAS; `fulfillCaptured` under `pg_advisory_xact_lock(paymentId)` + `claimX402Settlement` receipt claim + settle CAS re-asserting `status='settling'` and `txSignature` → mint exactly once ([agent-pay.ts:268-322](../../apps/api/src/services/agent-pay.ts#L268)). (The *machine* is sound; F1 is about the *policy* it enforces.)
- **x402-checkout** (`services/x402-checkout.ts` + route) — on-ramp-gated 503 (not live), per-checkout mutex + fast idem replay + one-tx flip+fulfill + 23505 replay; refuses non-ledger agent sessions.
- **wallet-withdraw-executor** — DARK (`WALLET_WITHDRAW_ENABLED` default off); claim-before-sign, capture-before-send, forward-only reconcile, `(subject, avatar, idempotency_key)` partial-unique; custody keypair verified against row `public_key` + `avatars.wallet_address` mirror, never cached/logged/returned. `wallet.secretKey` exactly-once holds on every traced path (connect/reconnect/signup all conditional on first-insert).

- **Quests submit / bounty approve** — single status-CAS (`WHERE status IN(...)` / `WHERE status='submitted' RETURNING`) with the credit inside the same tx; concurrent double-approve credits once ([quests.ts:878-919](../../apps/api/src/routes/quests.ts#L878), [bounties.ts:1086-1148](../../apps/api/src/routes/bounties.ts#L1086)).
- **Guest→real contamination** — cove `getSubject` 401s an expired/invalid agent session and 403s a non-ledger/avatarless one; it NEVER falls through to guest ([cove-slots.ts:327-362](../../apps/api/src/routes/cove-slots.ts#L327)). Guest and ledger sessions are keyed distinctly; guest play never touches the ledger. (Note: `/api/world` DOES demote an invalid agent header to guest, but the world layer settles no money.)

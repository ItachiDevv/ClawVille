# Perf Round-3 — Baseline & Diagnosis (2026-06-15)

Measured on `staging.clawville.world/game?perf=1` via chrome-devtools MCP performance trace + first-party instrumentation globals (`__CV_VRM_LOAD_METRICS`, `__CV_TEXTURE_UPLOAD_METRICS`, `__W3D_*`).

> ⚠️ **Tooling caveat:** the chrome-devtools MCP browser is **software-rendered** (`glRenderer: "WebKit WebGL"` / SwiftShader behind the WebGPURenderer). Absolute GPU-compile and upload times are **inflated** vs the user's real Iris Xe. Structural findings (what dominates, ordering, serialization) are valid; absolute ms are not the user's experience. Real-machine before/after sign-off required.

## Headline: steady-state is fixed; the load phase is the remaining cost

### Steady-state (post round-2) — GOOD, do not touch the frame loop
- **82 FPS avg**, frame avg 12.2ms, **p50 12.5ms, p95 16.8ms**, max 33.2ms, only **1 long frame (>33ms) in 179 samples**.
- Round-2 freeze fix (O(1) terrain heightfield) + VRM decimation landed and hold. Scene: ~423k tris, ~576 draw calls/frame, 69–81 skinned meshes.

### Load phase — ~10s warm / ~22s cold to fully ready. THE round-3 target.
Three serialized costs, all self-throttled as if protecting a frame budget that does not exist while the loading overlay covers the scene:

1. **Shader/pipeline compile — `_completeCompile` = 7.5s main-thread self-time** (software-rendered; less on real GPU but still #1 main-thread load cost). Root cause: `PreCompilePipelines` calls `gl.compileAsync(scene,camera)` **once at mount**, but the **14 VRMs load asynchronously over the next ~10s** → their skinned-`MeshStandardMaterial` pipeline variants are NOT in the scene at precompile time → they compile **lazily at first render**, smeared across the load. (VRMs use MeshStandardMaterial, 266 instances / 81 skinned — **not MToon**, mtoonMaterials=0.)
   - Confirmed by per-VRM `parseMs` decay: first VRMs 3990ms/3999ms/1988ms/2000ms, a same-size later one **74ms** — classic one-time pipeline warm-up cost paid by the early arrivals.

2. **Texture upload tail — 10–17s wall-clock** (179 textures). `StaggeredTextureUpload` sips **4 textures / 6ms idle-slice** to "never steal the frame budget." During the loading screen there is no visible gameplay frame to protect (loading screen is a CSS overlay), so this throttle just stretches the wait. This is the band the user sees stuck at ~80%.

3. **VRM parse queue — serialized, queue-wait up to 9.6s.** `vrm-loader.ts` runs **concurrency=2** with idle-callback pumping. Tuned for steady-state remote-player joins, but during the initial bulk load it serializes 14 parses behind each other.

### Loading bar — bands rebalanced + slow-hint self-calibrated (S1, 2026-06-16)
`sea-loading-screen.tsx`. Two playtest complaints fixed:
- **"Taking longer than expected" fired on every cold load.** Change D's fixed `SLOW_MS=8_000` sat *below* the real load (~10s warm / ~22s cold) so it was noise. Replaced with a self-calibrating threshold: each successful mount→`__W3D_READY` is recorded to `localStorage['cv_last_load_ms']`, and the hint fires only at `max(12s, lastLoad × 1.8)` (first-ever load defaults to 22s). `TIMEOUT_MS` 30s→45s so cold Iris Xe isn't force-dismissed mid-load.
- **Bar jumped to ~60% instantly.** `__W3D_PROGRESS` (= `loaded/total`) only tracks GLBs — VRMs use raw fetch and are invisible to it — so the GLB batch draining spiked the ratio to ~1.0 and the old 0.60 download band credited the full 60% via the ratchet while VRM-parse + the dominant 10–17s upload + compile still lay ahead. Bands rebalanced to match real wall-clock: download **[0,0.30]** · upload **[0.30,0.85]** (the incrementally-tracked dominant phase gets the biggest slice) · compile **[0.85,0.97]**. The download band is additionally time-eased (`min(downloadFrac, elapsed/4s)`) so the LoadingManager total-drain spike climbs from 0 rather than snapping to the ceiling; a new `preparing` ("Preparing scene…") phase covers the GLB-done-but-upload-not-started gap. Ratcheted + `__W3D_READY` dismiss unchanged.

### Service worker — NOT a bottleneck
First trace pass mis-attributed 62s to `sw.js staleWhileRevalidate` (node-id collision across threads). Per-thread split: the SW thread is **99.9% idle** (~5ms real work). Ignore.

## Round-3 thesis
**Loosen every load-time throttle while the loading overlay is up; restore gentle pacing the moment the world is interactive.**
- Re-run `compileAsync` (or a targeted pipeline warm) once the VRM batch is in-scene, so skinned-Standard variants compile in one async pass under the spinner (KHR_parallel_shader_compile is available) instead of lazily at reveal.
- Texture upload: large slices (or full blast in bounded long-tasks) while overlay visible; fall back to 4/6ms idle-slicing once `__W3D_READY`.
- VRM parse: higher concurrency during the initial bulk load; back to 2 for steady-state joins.

## Constraints (do not regress)
- **No quality loss** (hard user rule).
- **Iris Xe**: no drei `<Text>`/`<Billboard>`, no `InstancedMesh+ShaderMaterial`, no per-frame `new Vector3` in useFrame.
- **First-paint / blue-screen history**: World3DCanvas has prior blue-screen regressions from render/upload-lifecycle changes (OpaqueCanvasClearGuard double-render; WebGL2 camera.aspect=0 NaN; WebGPU swapchain pre-config). Any change to upload/compile timing must preserve `forceFirstPaintSizeSync` + the two-rAF gate + `__W3D_READY` semantics.
- Verify relative time-to-`__W3D_READY` before/after on the sandbox; require user real-machine sign-off (Rule E4).

## Implemented (2026-06-15)

All four changes shipped to `perf/round3` branch, worktree `ClawVille-perf-r3`. Working tree dirty — not pushed/deployed.

### Change A — Second `compileAsync` after VRM batch settles
**File:** `apps/web/src/components/three/World3DCanvas.tsx` (`PreCompilePipelines`)
**File:** `apps/web/src/lib/three/vrm-loader.ts` (new export `registerBulkVRMIdleCallback`)

`vrm-loader.ts` now exports `registerBulkVRMIdleCallback(cb)`. The callback fires exactly once when `vrmParseActive === 0 && VRM_PARSE_QUEUE.length === 0` — i.e. the initial VRM parse batch has fully drained. If the batch was already idle when the callback is registered (e.g. no VRMs at all), it fires via `Promise.resolve().then(cb)` on the next microtask tick. `PreCompilePipelines` calls this from inside its existing `requestAnimationFrame` after the first `compileAsync`, and fires a second `gl.compileAsync(scene, camera)`. At that point all VRM `SkinnedMesh` / `MeshStandardMaterial` instances are in the scene, so their skinned-Standard pipeline variants get compiled once under the spinner rather than lazily at reveal.

Safety invariants preserved:
- No `gl.render()` call inside the callback (blue-screen safe).
- Guard: `typeof (gl as any).compileAsync === 'function'` (same as existing call).
- The callback fires via `requestIdleCallback` with a 200ms timeout (Safari falls through to `Promise.resolve`).
- Sets `window.__W3D_VRM_COMPILE_DONE = performance.now()` for tracing.

### Change B — Fast texture upload while loading overlay is up
**File:** `apps/web/src/components/three/World3DCanvas.tsx` (`StaggeredTextureUpload`, constants block)

Added three fast-mode constants:
- `FAST_SLICE_BUDGET_MS = 30` (was 6ms cap for steady-state)
- `FAST_MAX_TEXTURES_PER_SLICE = 32` (was 4)
- `RAF_FAST_BATCH = 24` (was 4)

Added `isLoadingOverlayUp()` — returns `(window as any).__W3D_READY !== true`.

`uploadIdle` and `uploadRafFallback` both call `isLoadingOverlayUp()` at the top of each slice to pick the correct budget/cap pair. The switch happens per-slice, so if `__W3D_READY` is set mid-upload (edge case: upload finishes just before/after reveal) the pacing automatically relaxes.

All preserved exactly:
- Two-rAF gate before texture scan.
- `markTextureUploadReady()` → `gl.render(scene, camera)` + `__W3D_TEXTURES_READY = true` + `markWorldReadyIfUploadsDone()`.
- `__W3D_TEXTURE_UPLOAD_TOTAL` / `__W3D_TEXTURE_UPLOAD_DONE` counters.
- `createTextureUploadMetrics` / `pushTextureUploadSlice` / `completeTextureUploadMetrics` pacing metrics.

### Change C — Dynamic VRM parse concurrency
**File:** `apps/web/src/lib/three/vrm-loader.ts`

`VRM_PARSE_CONCURRENCY = 2` constant removed. Replaced with:
- `VRM_PARSE_CONCURRENCY_BULK = 6` (during initial bulk load)
- `VRM_PARSE_CONCURRENCY_STEADY = 2` (after `__W3D_READY`)
- `getVRMParseConcurrency()` — reads `window.__W3D_READY` and returns the correct limit.

`pumpVRMParseQueue` updated:
- `while (vrmParseActive < getVRMParseConcurrency() ...)` — dynamic limit.
- After the while-loop: `if (vrmParseActive === 0 && VRM_PARSE_QUEUE.length === 0) _fireBulkIdleCb()` — drain detection for Change A.

All preserved exactly:
- Priority lane: `PLAYER_INSTANCE_ID = 'player-avatar'` tasks are `unshift`-ed to front of queue.
- Generation-based cancellation (`VRM_LOAD_GEN`, checked at parse-start).
- `enqueueVRMParse` / `cacheKey` / `gen` options unchanged.

### Change D — `SLOW_MS` 15s → 8s
**File:** `apps/web/src/components/game/sea-loading-screen.tsx`

`SLOW_MS` reduced from `15_000` to `8_000`. With changes B+C the expected warm load is ~5–7s on a real Iris Xe. 8s gives comfortable margin. `TIMEOUT_MS = 30_000` unchanged; composite bar bands, ratchet, and `__W3D_READY` dismiss logic unchanged.

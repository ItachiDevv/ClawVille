# Adversarial review: Cold-Load Diet

## 1. VERDICT

**REJECT** — the high-level scope cut is right, but workstream A chooses a boundary after assets can already render, its fail-open path can become permanent omission, and the proposed work cannot reach the stated 10 MB reveal target under its own accounting.

## 2. Findings

1. **[BLOCKING] “Discovery time” is not a safe reveal boundary** — The current machinery has one `seen` set, one `discoveredTotal`/`uploadedDone` pair, one `uploadQueue`, and one mutable `activeUploadResolve` (`apps/web/src/components/three/World3DCanvas.tsx:1520-1534`, `:1600-1604`, `:1624-1640`, `:1711-1718`). `startPostReadyScans()` calls the same scanner and uploader two seconds after reveal, so it still grows the reveal counters and increments `uploadedDone` (`:1759-1776`). Merely adding a second Promise queue would also race the single `activeUploadResolve`. More importantly, by the time a post-reveal scan sees a texture, React/R3F has already committed the mesh and the live frameloop can draw it. The late scan cannot prevent the first-frame texture upload or shader compile. The VRM bulk compile callback is intentionally one-shot (`apps/web/src/lib/three/vrm-loader.ts:223-280`), while the post scan does no object compile and stops after 60 seconds. The plan also misstates the present symptom: a larger late `TOTAL` can lower the raw ratio, but the displayed bar is ratcheted and cannot move backward (`apps/web/src/components/game/sea-loading-screen.tsx:288-291`), and `__W3D_READY` is latched rather than re-gated. **Fix:** make scene membership/resource readiness the boundary. Decorative objects must be absent from the boot scene, and each parsed object must pass a separate, event-driven post-reveal texture-upload plus `compileAsync(object, camera, liveScene)` resource before it is committed visibly. Keep a single serialized GPU scheduler with explicit `reveal` and `post` counter lanes; never call the reveal counter publisher for the post lane. The concrete seam is sketched in section 4.

2. **[BLOCKING] The 45-second fail-open can silently become “never load the NPCs”** — The normal world gate's 40-second fuse sets `__W3D_TEXTURES_READY` and recombines readiness (`World3DCanvas.tsx:1105-1116`, `:1152-1166`), but `SeaLoadingScreen`'s independent 45-second force-dismiss only changes local React state; it does not set any world-ready global (`apps/web/src/components/game/sea-loading-screen.tsx:177-187`). The existing `DeferredNpcPreloads` polls `__W3D_READY` forever with no ceiling (`apps/web/src/lib/three/arena-location-npcs.tsx:827-850`). If A copies that pattern for mount release, an unusual gate/lifecycle failure can hide the loader at 45 seconds while every deferred NPC remains omitted forever, violating timing-only deferral. Stage returns add another trap: the hosted world acknowledges immediately after its first warmup (`apps/web/src/components/three/world-stage/StageHostedWorldScene.tsx:27-38`), so a release state tied to a fresh stage warmup may never fire. **Fix:** introduce a one-shot `decorativeReleased` controller that fires on normal gate resume, either 40-second world/stage safety resume, or its own absolute deadline no later than the loader ceiling. It must survive stage transitions and never reset after first release. Every per-object post-warm task also needs a bounded fail-open that resolves to visible rather than suspending forever. Test normal completion, forced warmup error, no-progress fuse, 40/45/60-second ceilings, background-tab/no-`requestIdleCallback`, SPA return, and world→activity→world.

3. **[BLOCKING] “Defer the wanderer VRMs” is neither a 13-file nor a path-level operation, and parse completion does not guarantee “no T-pose”** — The manifest's 13 paths exclude Ansem and Adinero (`apps/web/src/lib/three/asset-preload-manifest.ts:118-138`); both probes contain 15 byteful VRM requests totaling 12.192 MB. Eleven paths are also fetched at module evaluation (`apps/web/src/lib/three/arena-npcs.tsx:455-476`) and all 13 manifest paths are fetched by `preloadWorldAssets()` (`asset-preload-manifest.ts:269-300`). Delaying JSX alone therefore does not delay those bytes. Conversely, globally classifying `/avatars/ansem.vrm?v=1` as deferred is wrong because Ansem is also an exclusive player-capable model (`apps/web/src/lib/three/agent-model-registry.ts:202-211`), while the same URL renders `ansem-wanderer`. Own-player and remote demand must win naturally even when a decorative NPC shares the URL. Finally, `ArenaNpcs` is not just decorative wanderers: it maps the live store and only filters `PLAYER_NPC_ID` outside NPC mode (`apps/web/src/lib/three/arena-npcs.tsx:1658-1676`); the store merges autonomous avatar bodies into that same array (`apps/web/src/stores/npc.ts:739-753`). Suspense prevents a *partially parsed* VRM from mounting, but the `<primitive>` commits immediately after parse while `VRMCharacterAnimator` is only constructed in a post-commit effect and `animator.init()` remains asynchronous (`arena-npcs.tsx:1109-1142`, `:1552-1561`). The animator does not mark itself ready until clips are retargeted, and it awaits Ansem's attachment before `init()` resolves (`apps/web/src/lib/three/vrm-character-animator.ts:835-886`; attachment fetch is `apps/web/src/lib/three/character-attachments.ts:79-96`, `:156-169`). The plan's parse-at-mount guarantee is therefore false: rest/T-pose and sword pop-in remain possible. **Fix:** remove the module-scope and manifest-wide wanderer byte preloads; keep player/remote components demand-driven and reveal-priority. Delay only explicitly tagged static ambient NPC IDs, never the whole `ArenaNpcs` subtree, `PLAYER_NPC_ID`, autonomous avatars, or real remote players. Keep SSE/store updates running and derive the delayed render list from the *current* store at release—never capture the demo roster. The detached VRM resource must await parse, animator initialization (including attachment), evaluate the initial mixer pose once, upload textures, and compile the object before resolving visible. Test a live demo→server roster swap during deferral, Ansem as the local avatar while Ansem NPC is delayed, deliberately slow animation/attachment responses with frame-by-frame capture, NPC possession, autonomous bodies, remote joins, parse rejection/retry, and one network fetch for a shared path.

4. **[BLOCKING] The named “deferred preload” components are not the demand boundary** — Location preloading already waits until `__W3D_READY` (`arena-location-npcs.tsx:805-850`), yet all 12 location assets arrive before reveal because the actual `NpcMesh` calls `useGLTF()` (`:424-429`) and the 4,600-unit resident threshold deliberately mounts the entire 4,160-unit building ring from spawn (`:56-65`, `:742-763`). Changing `DeferredNpcPreloads` cannot change boot demand. Terrain is the opposite: `DeferredTerrainPreloads` still fires on the first `requestAnimationFrame`, not after reveal (`apps/web/src/lib/three/arena-terrain.tsx:660-684`), and mounted terrain components can demand the same files anyway. **Fix:** put the release check in the parent *before* rendering the components that invoke `useGLTF`/`useVRMInstance`; then make any proactive preloader consume the same release signal. Add a probe assertion that no deferred URL begins before `decorativeReleasedAt`, rather than accepting a comment or preload-call timestamp as evidence.

5. **[BLOCKING] The 10 MB reveal target does not close arithmetically** — In the measured fixture, removing all 15 VRMs (12.192 MB), all 12 location GLBs (6.712 MB), Ansem's sword (0.348 MB), and their character-specific animation files (0.417 MB) from 34.62 MB leaves about **14.95 MB** pre-reveal. The plan's “~21 MB” uses a ~9 MB location estimate not present in either full request list and credits a 2.2 MB `_emotes.glb` saving that is not on the reveal path. The headed report instead requests `_emotes2.glb?v=1` (0.518 MB) at 71.7 seconds; `_emotes.glb?v=1` is demand-loaded on first matching emote (`apps/web/src/lib/three/vrm-character-animator.ts:133-148`) and does not occur in either pre-reveal inventory. After A, decimating Ansem/Adinero/chibis and dieting most location textures lowers *post*-reveal bytes, not the remaining reveal wire. The only named large core savings are mainly pavilion and shisha, which still do not bridge roughly five MB. The target is also avatar/presence-dependent: the plan keeps the local avatar and every real remote avatar reveal-gated, so an Ansem owner or a populated room changes the mandatory bytes. **Fix:** add an exact URL allowlist and spreadsheet/scripted sum for each milestone: baseline, A-only reveal, A+B/C reveal, and eventual stream. Define a reproducible avatar/room fixture and report additional worst-case local-avatar and populated-room variants; do not present 10 MB as an invariant if remote arrivals remain in the gate. Either expand deferral beyond the declared core, add concrete diets to still-gated assets, or revise the target. Define “total cold session” by a deterministic queue-drained marker and timeout; interaction-triggered emote downloads cannot be part of an undefined session endpoint.

6. **[MAJOR] The claimed proportional 13-second win is not established, and the target omits the next user-visible stalls** — The reports know network timing, coarse readiness samples, and long tasks, but not the time spent in LoadingManager barrier, VRM parse drain, stable scans, texture slices, scene compile, or warm draw. Those phases exist separately and are already timed in code (`World3DCanvas.tsx:1844-1953`), but their values were not captured in the reports. The approximately 4.7 seconds of long tasks do not explain the whole post-network interval; “cuts roughly proportionally” is therefore a hypothesis. Backend also matters: low-end/integrated GPUs, including the Iris path, default to WebGL2 (`:2458-2495`), where the controlled warm draw pays synchronous shader work (`:1932-1946`); this is not simply a WebGPU pipeline floor. Moving work after reveal can hit the user's first movement instead of improving it: after-ready VRM parsing drops to concurrency two (`apps/web/src/lib/three/vrm-loader.ts:197-219`), while there is no post-reveal frame-time or queue-completion SLO. **Fix/experiment:** export phase timestamps/counters and renderer backend into the probe; run isolated A/Bs for ambient VRMs, location GLBs, pavilion, and all ambience, with a fixed avatar/presence fixture. Add loader first-contentful-paint, canvas first present, overlay gone, first 10 stable frames, worst long task/frame in the first 10 seconds after reveal, first ambient NPC visible, all ambient NPCs visible, and post queue drained. Treat 8 seconds as provisional until this experiment demonstrates it on both desktop backend and Iris WebGL2.

7. **[MAJOR] The mandated opacity fade conflicts with the round's mutation constraints** — A per-object 0.5–1 second opacity fade is not load orchestration. It requires changing `transparent`/opacity across every PBR/MToon material, compiling transparent variants, and usually cloning materials to avoid shared-cache corruption. Location NPCs use `SkeletonUtils.clone(scene)` and explicitly rely on shared/tinted material caches (`apps/web/src/lib/three/arena-location-npcs.tsx:447-464`, `:503-513`). Mutating those materials can fade another consumer such as the shared lobster plush; cloning creates new material instances, which the hard constraints disallow. **Fix:** under the stated constraints, reveal an object atomically only after its detached resource warmup completes. If a fade is non-negotiable, explicitly widen the round to a renderer/material change, precompile the transparent variants, prove no shared-material mutation, perform no per-frame allocation, and requalify Iris Xe. The current plan cannot promise both.

8. **[MAJOR] “UASTC → ETC1S for non-color maps” groups together maps with very different error tolerance** — ETC1S is a reasonable wire format for many masks/roughness/AO textures, but normal maps are sensitive to block/endpoint error and can turn broad stylized highlights into visibly faceted or crawling lighting. A single gameplay screenshot is also weak because the defect is worst under grazing or moving light. **Fix:** make the choice per texture semantic and asset. For these distant cartoon characters, first test removing the normal map; if the gameplay-distance difference is below the agreed visual threshold, removal wins on wire, upload, sampler count, and possibly program complexity. If the normal contributes, test **512 UASTC+zstd** (and 256 for the plush) before ETC1S; it preserves normal fidelity while cutting texels 4×. Use ETC1S for normal maps only after an asset-specific orbit/grazing-light A/B passes. Test color, normal, and packed data maps separately; do not use “non-color” as the policy. For pavilion atlasing, first group images by material, color space, wrap mode, and UV compatibility—66 files alone does not prove that an atlas reduces wire or pipelines.

9. **[MAJOR] Ansem's byte problem is vertex topology/attribute entropy, not an embedded-animation or morph-target mystery; 35k is still an arbitrary quality decision** — Direct GLB inspection found one mesh/primitive, no morph targets, one 24-joint skin, and a tiny embedded animation payload. The primitive has about 193,946 vertices for 118,167 triangles; its meshopt streams are dominated by position, normal, UV, weights/joints, and indices. In particular, the near-split indexed topology and large normal/position/UV streams—not the animation—explain most of the 2.7 MB. Triangle reduction may help, but it can damage the promo silhouette, coat, face, hands, skin deformation, and sword alignment, and a fixed triangle count does not address avoidable duplicate vertices or attribute precision first. The established script also validates 38k–42k triangles, not the plan's 35k target (`scripts/decimate-vrm.ts:437-466`, `:520-524`). **Fix/experiment:** first produce an accessor/meshopt byte census, exact-tuple weld dry run, UV/hard-normal seam audit, component/quantization check, and vertex-cache/overdraw analysis. Then generate sibling prototypes across a rate-distortion ladder (for example 90k/60k/45k/35k) and choose the visual knee, not a preselected number. Validate idle/walk/run, shoulder/hand/face deformation, sword hand/back attachment, silhouette and promo close-ups, grounding/bounds, VRMC extensions, and runtime load. Parameterize the script's target band. For the chibis, use the repository's VRM-safe capture/reinject pipeline—stock glTF transforms strip unknown `VRMC_vrm` data, as documented in `scripts/assets-optimize.ts:12-19`—and treat Ansem already loading with meshopt as positive evidence for runtime decoder compatibility, not evidence that arbitrary VRM conversion preserves metadata.

10. **[MAJOR] “SW-covered” is not a verification plan and the explicit precache does not cover the declared core** — `PRECACHE_GLBS` includes lobster, a few terrain assets, the 11 buildings, and locomotion (`apps/web/public/sw.js:69-100`), but not the pavilion/bazaar/shisha town props, player VRMs, or location NPCs. Other assets become warm only after runtime cache-first sees their exact request URL (`:224-275`). Timing deferral therefore changes whether an interrupted first visit ever populates them. Query/sibling mutations are also exact cache keys: every runtime, manifest, attachment, and precache reference must move together. Keeping the same cache namespace leaves superseded query entries consuming the 60 MB budget; blindly bumping it deletes all old runtime warmth on activation (`:59-67`, `:199-217`). **Fix:** define the reveal-core URL set and make the SW precache cover it exactly, including mutated town-prop URLs. Add an automated URL-parity test. Choose and test an upgrade policy: either bump the namespace and accept/measure the one-time refill, or prune superseded URLs without deleting unrelated warm assets. Verification must be a real sequence: clean install → first reveal → post queue drain → second navigation; then old-build cache → new SW activation → navigation. Assert core request/SW-hit behavior, eventual NPC presence, and cache size/eviction.

11. **[MAJOR] Strict A-first sequencing maximizes the chance of shipping a fast reveal followed by a frozen first interaction** — A is the only workstream capable of changing reveal architecture, so B/C-first alone is not defensible. But widening A to every ambient asset before proving detached prewarm moves today's very large VRM/texture/compile cost directly into live play. **Fix:** sequence as (0) phase instrumentation, exact allowlist arithmetic, and fixed test fixture; (1) an A skeleton/canary for one location GLB that proves counter isolation, detached upload/compile, all watchdogs, stage return, and SW behavior; (2) B/C variants for the largest future post-reveal assets so their streaming cost is bounded; (3) widen A class-by-class, re-probing reveal and the 10-second post-reveal frame SLO after each class; (4) D only after critical-path evidence. This preserves A's architectural priority without treating unmeasured post-reveal jank as success.

12. **[MINOR] The probe cannot settle the HTTP/2, Cloudflare, priority, or `/login` theories used in D** — Each request record contains URL, timing, bytes, SW/cache flags, type/MIME/status, but not protocol, initiator stack, initial/changed priority, `CF-Cache-Status`, `Age`, or server timing. The six `/login` RSC requests total only a few KB; they matter only if their priority/connection scheduling delays critical assets. **Fix/experiment:** capture `Network.requestWillBeSent` initiators, `resourceChangedPriority`, response protocol and CF headers. Disable the responsible Next.js prefetch at its source in an A/B and keep the change only if critical request starts/reveal improve. Do not infer a multiplexing or edge-cache win from request count alone.

## 4. Replacement reveal-boundary seam for workstream A

The clean seam is **before object commit**, not “which scan discovered the texture.”

1. In `World3DCanvas.tsx`, add a one-shot `decorativeReleased` state/context owned by the persistent world scene. Release it from the existing warmup gate's `onResume` for normal completion and safety resume, from the stage-ready path, and from an independent absolute deadline no later than 45 seconds. Never set it false on stage transitions. Do not change `markWorldReadyIfUploadsDone()`, the 60-second canvas-ready reassert loop, or the 40-second warmup fuse.

2. Refactor the texture scheduler in `World3DCanvas.tsx` to accept `lane: 'reveal' | 'post'`. Keep one serialized Promise queue and one active resolver. Give each lane its own `seen`, total, and done values. Only the reveal lane publishes `__W3D_TEXTURE_UPLOAD_TOTAL/DONE`; optional post metrics use new names and have no relationship to `__W3D_READY`. Remove the polling-only 60-second post scanner as the primary mechanism; retain a counter-isolated best-effort scan only as a safety net.

3. Add an event-driven `warmDeferredObject3D(object, renderer, camera, liveScene)` resource. For a VRM, first construct and await its one owning `VRMCharacterAnimator`—including initial clips and configured attachment—evaluate the mixer once at time zero so the first visible frame is posed, and retain that animator for the component rather than constructing a second one after commit. Then traverse the complete detached object, queue its textures through the post lane, temporarily disable/restore mesh frustum culling, and call `renderer.compileAsync(object, camera, liveScene)`. Cache the Promise/status by object+renderer. A React wrapper throws that Promise under Suspense, so the object is not attached visibly until preparation, texture upload, and compile finish. Its no-progress/absolute ceiling resolves fail-open to visible; it never leaves an NPC suspended forever. This uses the installed Three API's object-plus-target-scene compile path and introduces no ShaderMaterial, InstancedMesh, drei text, or per-frame allocation.

4. In `asset-preload-manifest.ts`, stop calling `preloadVRMBytes()` for the blanket wandering list during boot. In `arena-npcs.tsx`, remove the equivalent module-scope byte preloads. Keep locomotion and actual local/remote avatar demand reveal-priority. A URL shared by player and wanderer then fetches early only when critical demand actually exists.

5. In `arena-npcs.tsx`, continue subscribing to and updating the whole live roster. Split only rendering into critical and explicitly tagged ambient IDs. Render critical/possessed/autonomous/real-player bodies immediately; render the current ambient subset after `decorativeReleased`, with each VRM passing through the detached warm resource. Do not snapshot `DEMO_NPCS` at release scheduling time.

6. In `arena-location-npcs.tsx`, apply `decorativeReleased` in the parent before creating any child that calls `useGLTF`. Make `DeferredNpcPreloads` use the same release controller or remove it in favor of the ordered post resource queue. Apply the same rule to any terrain decoration actually moved out of the core.

7. Under the hard constraints, mount each warmed object atomically. Delete the fade promise from the plan unless material/render changes are separately authorized and Iris-qualified.

8. Add tests/instrumentation that assert: reveal counters freeze at release; post counters cannot affect loader progress or readiness; every deferred ID eventually mounts through normal/error/timeout paths; current SSE positions are used; player/remote shared URLs retain priority; stage return does not re-gate or omit; and no deferred request starts before the release marker unless a critical consumer shares that exact URL.

> Persistent money-domain memory for the `cove` agent (slots, blackjack, baccarat, hold'em, poker MTT, poker cash). **Precedence: live code > canonical docs (ARCHITECTURE.md / GameFeatures.md) > this memory.** A fix merged to a branch is NOT live on prod until the container flips — verify git + the prod container before trusting any "FIXED"/"LIVE" claim here. ## Invariants — the money contract (never violate)
1. CT-ONLY: every cove game settles ClawTokens exclusively. currency enum is clawtokens|sol|usdc but SOL/USDC return 501 CURRENCY_COMING_SOON at session/open (cove-blackjack.ts:802, cove-slots.ts:538). The wager Anchor program is devnet-gated and is NEVER on the cove CT path; txSignature stays NULL on all fun-money rows.
2. LEDGER-ONLY: real CT moves ONLY through claw-token-ledger debitClawTokens/creditClawTokens/transferClawTokens on avatar.id. NEVER write avatars.clawTokens directly — that bypasses the FOR UPDATE row-lock + balance>=0 assert (InsufficientTokensError) + claw_token_transactions balanceAfter insert (claw-token-ledger.ts). A direct avatars.clawTokens write is a bug, full stop.
3. SUBJECT-KEYING KEYSTONE: events are keyed userId XOR guestFpHash (DB check constraints cove_game_events_subject_check + slot_sessions_subject_check). The WRITE path getSubject AND the READ/history/verify/claim path resolveSubject MUST resolve the SAME THREE subjects {user, agent, guest} via the SAME resolveAgentSession. If they drift, an agent's real-CT rows vanish into the guest tier ('won 20 CT, no history'). Adding ANY new game means adding it to BOTH paths same diff.
4. AGENT PARITY (Rule E5): isLedgerSubject() collapses user+agent so real-CT settle code is written ONCE. An agent plays AS ITSELF via X-Clawville-Agent-Session -> resolveAgentSession -> bound avatar userId. An agent is NEVER demoted to guest on a money path: unknown/expired -> 401, !ledgerCapable -> 403 agent_session_not_ledger_authorized, bound-but-no-active-avatar -> 403 agent_session_has_no_active_avatar. A logged-in human cookie always wins over a smuggled agent header.
5. GUEST-DEMO ISOLATION: guests are demo-only. Their balance lives on the session/shoe row (startingBalance + won - staked), and NEVER touches avatars.clawTokens (cove-slots.ts:770 'we never write avatars.clawTokens for guests'). Guests are 403'd from every lifecycle/recovery/inspect endpoint and feed nothing persistent (no leaderboard, no ledger).
6. ATOMIC SETTLE TX: every settlement runs in ONE db.transaction with the parent row (shoe/session/table/tournament) SELECT ... FOR UPDATE first. Under the lock: re-assert ownerMatch (never trust caller pre-checks), re-load the hand bound to (id, parentId) not id alone, assert cursor/dealt drift (else fail closed), RECOMPUTE the engine under the lock (a stale pre-lock read must never commit a divergent outcome), then debit+credit. All-or-nothing. EXCEPTION/OPEN: cash-table-manager.ts opens NO db.transaction (HIGH bug, local-only).
7. IDEMPOTENCY ANCHORS: client Idempotency-Key + a DB partial-unique index is the race-safe backstop on every settle/spin/coup ((sessionId,idempotencyKey), (shoeId,idempotencyKey)+(shoeId,coupIndex), (tableId,idempotencyKey)). A 23505 collision ABORTS THE WHOLE TX (rolling back the in-tx debit/credit) and is re-read OUTSIDE the aborted tx as a replay (IdempotencyReplayError) — never 'fix' it by reading inside the failed tx. Status flips in_progress->settled exactly once via compare-and-set UPDATE ... WHERE status='in_progress'. Same key + different stake/args -> 409, never a second charge.
8. OWNER CHECKS: ownerMatch keys a ledger subject (human OR agent) by parent.userId and a guest by guestFpHash. Because an agent and its bound human share ONE userId, they share ONE session/shoe — the agent CONTINUES the human's session, never forks a parallel one. Foreign hand/event ids 403/409. Re-assert under the settle lock as defense-in-depth.
9. PROVABLY-FAIR COMMIT-REVEAL: serverSeedHash = sha256(serverSeed) published at open; serverSeed REDACTED while status='open' (publicSession/publicShoe null it); revealed on EVERY cove_game_events row only at parent close. Engine re-derives every card from (serverSeed, clientSeed, nonce, cursor) via HMAC; the client NEVER sends cards/outcomes. Poker publishes serverSeedCommitHash in the public snapshot BEFORE the hand resolves (poker-table-sim.ts:276).
10. NO BOARD-LEAK: an in-progress response must NEVER reveal undealt community/hole cards. Blackjack serializes ONLY dealerUpcard (never the hole card or dealer playout). Hold'em truncates peek.board to visibleBoardCountForStreet (preflop 0/flop 3/turn 4/river 5) — the synthetic-fold peek deals all 5 internally; returning peek.board un-truncated re-opens the leak (the exact holdem board-leak bug, b23b4231). Poker state-for-agent returns only the requesting subject's own view.
11. VERIFIER CANONICALIZATION: jsonb does NOT preserve object key order, so ANY verifier comparing engine output to a jsonb-stored outcomeJson MUST use cove-verify-compat.ts canonicalize()/canonicalJsonEq (sorts object keys, PRESERVES array order for cards/reels/lines), never raw JSON.stringify. verified:null (not false) means open-shoe or engine-not-yet-shipped — not a fairness failure.
12. CONSERVATION BY CONSTRUCTION: poker prize math is bigint throughout — rake=(pool*rake_bps)/10000n, computePrizes floors each share, then settle FOLDS THE ROUNDING REMAINDER INTO 1ST PLACE so Sum(prize)+rake == pool EXACTLY (tournament-manager.ts:1846-1860). Chip conservation: post = start - totalCommitted + won (never mints). Cash chips == CT 1:1; seeded-agent chips MUST be real-CT-backed by a house-bank debit or fillSeededAgents THROWS seeded_agent_requires_house_bank.
13. STAGING-FIRST + ADVERSARIAL-MONEY-AUDIT DISCIPLINE: cove money/parity code goes to staging first, never direct to master (override = literal 'direct to master'). Any change to settle/idempotency/ownership/agent-session/SSRF/custodial-wallet on the cove gets a full backend team + Codex adversarial pass + LIVE staging smoke asserting hidden-state invariants (board==street-count, no opponent cards mid-hand, seed null until close) — bun test green is NOT a substitute (the holdem board-leak passed audits, only live smoke caught it). The MTT agent action surface is the PROTECTED PARTNER SURFACE: requires Codex pass + mock-Hatcher harness GREEN + PROTOCOL_VERSION bump.

## Open issues (severity-tagged, file-anchored)

### HIGH
- **Cash poker money writes are NOT DB-transactional** — `cash-table-manager.ts:541-587` (seatSubject) and `:652-709` (cashOutSeat) do debit→insert→update→insert as 4 separate round-trips with NO enclosing `db.transaction`; only an in-process `withTableLock` mutex (ZERO DB atomicity).

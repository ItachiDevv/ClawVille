## Known traps (read BEFORE any auth/session/identity change — feeds Phase 0)

- **Agent-session Map/row register race** → two concurrent registers for ONE agentId (hatcher register/PATCH, gateway /connect, openclaw /register): the in-mem openClawBots Map holds MANY sessionIds per agentId but the row holds ONE `session_key_hash`; both mint a bearer + write a hash + spawn a body, later DB write wins → the earlier 200-OK bearer is dead-on-arrival (present&&mismatch teardown) + duplicate avatar bodies → **guard:** in-process per-agentId `withKeyedMutex(namespacedAgentId)` wrapping a single `pg_advisory_xact_lock` tx that re-reads after acquire; atomic hash in the same upsert. NOT a pg lock nested under the cap lock. [[agent-session-map-row-race]] [[per-subject-serialization-mutex-advisory]] · FIXED + on prod.
- **Per-subject serialization (the fix pattern)** → any section mutating BOTH the DB row AND a process-local Map → **guard:** `withKeyedMutex(subjectKey)` (post-commit in-mem spawn) AND `pg_advisory_xact_lock` (cross-process, re-read after acquire); commit bearer hash in the SAME tx; outer lock first ALWAYS (agent→cap), nest inner; commit-first-spawn-after. [[per-subject-serialization-mutex-advisory]] · FIXED + on prod.
- **Fail-closed null-init lockout** → a strict `sessionKeyHash !==` reject on a NULLABLE column kills a freshly-minted partner session whose non-fatal hash-persist lands AFTER `registerOpenClaw` (the register→persist window) → **guard:** scope the reject to `present && mismatch` only (`bot.sessionKeyHash && bot.sessionKeyHash !== sha256Hex(sessionId)`, require-auth-or-agent.ts:166); a NULL hash falls through to the TTL gate. [[fail-closed-null-init]] · FIXED + on prod.
- **Subject-keying drift (E5 write-vs-read)** → a READ/history/verify/claim path resolves only {user,guest} (forgets the agent branch) while WRITE resolves {user,agent,guest} → the agent's userId-keyed rows fall through to guest, reads ZERO rows ('won 20 CT, no history', the live 2026-06-21 slots/history bug) → **guard:** every read path calls `resolveAgentSession` VERBATIM, same Lucia→agent→guest precedence keyed on userId; adding a game = same diff in BOTH paths + `GAME_TYPES` + a `/verify` branch + economy-monitor row. [[subject-keying-keystone]] · FIXED on prod for all casino games. **DRIFT: poker IS now wired** — `cove-history.ts:89 GAME_TYPES=['slots','blackjack','holdem','baccarat','poker']`.
- **Guest-demo isolation / agent→guest demotion** → routing an unbound/non-ledger AGENT to the guest tier on a money path (breaks the userId-XOR-guestFpHash constraint + demo accounting + Rule E5) → **guard:** WRITE path 401 unknown/expired, 403 non-ledger (`agent_session_not_ledger_authorized`), 403 no-active-avatar (`agent_session_has_no_active_avatar`) BEFORE any guest branch; guests never touch `avatars.clawTokens`; reads MAY soft-fall-through. [[guest-demo-isolation]] · FIXED + on prod.
- **Rotation-stale bearer keeps spending (R2-2)** → /connect or partner register/PATCH rotates the row's hash but the OLD bearer stays in the Map until restart, kept passing the (rotation-refreshed) TTL gate and spending the victim's CT → **guard:** on a live Map hit require `sha256Hex(sessionId) === bot.sessionKeyHash` (present&&mismatch teardown, :166) + resolve-time rebind re-validation `boundUserId===userId` (:280-294). [[bearer-ttl-gate]] [[ledger-rebind-revalidation]] · FIXED + on prod.
- **Stale-session ledger theft on ownership rebind** → attacker registers a ledger-capable session while an agentId is unbound/theirs, a later owned-token connect rebinds that row to a VICTIM, the frozen `config.ledgerCapable` would authorize the attacker → **guard:** two backstops (either alone closes it) — eviction-on-rebind in /connect+register (agent-gateway.ts:576-586) AND resolve-time demote-to-non-ledger + unregister when `config.boundUserId !== row.userId` (:289). [[ledger-rebind-revalidation]] · FIXED + on prod.
- **Un-awaited async resolver** → calling `getSubject`/`resolveSubject`/`resolveAgentSession`/`resolveActivityIdentity`/`validateLiveAgentSession` synchronously (agent branch hits the DB) returns a truthy Promise, silently passing the gate → **guard:** always `await` all five. [[async-resolver-await]] · invariant, no bug shipped.
- **FINGERPRINT_SECRET rotation = cascading invalidation** → rotating it to revoke dash access ALSO re-salts every `fp_hash` (resets anti-farm + leaderboard buckets) AND invalidates the HMAC-derived cv_dash cookie → **guard:** coordinate before rotating; prefer rotating `DASH_SHARED_PASSWORD` when fp buckets must be preserved; missing/<32-char secret crashes boot. [[fingerprint-stability-and-secret]] · OPEN (operational).
- **Spoofable client IP rotates rate-limit + fp key** → trusting `x-real-ip` or the FIRST x-forwarded-for entry lets a caller rotate the per-IP limiter / tier-2 fp bucket → **guard:** `getClientIp` = cf-connecting-ip → LAST x-forwarded-for → 'unknown'; x-real-ip REMOVED (FIX-18/SEC-6); all fp + limiter IP derivation flows through this one fn. [[fingerprint-stability-and-secret]] · FIXED.

## Invariants (the auth/session contract)
1. BEARER/TTL — ONE liveness gate: every bearer-trusting path (cove getSubject/resolveSubject, gateway perceive/move/chat, Milady→Lucia exchange, world presence) routes through `validateLiveAgentSession` (require-auth-or-agent.ts:107). Live ONLY when (1) sessionId is in the in-memory openClawBots Map OR restorable from the row, (2) the openclaw_bots row exists, (3) `session_expires_at` is NON-NULL and strictly > now. Map membership ALONE is NEVER sufficient — the DB row is the source of truth for liveness.
2. FAIL-CLOSED ON NULL TTL: a NULL `session_expires_at` is treated as EXPIRED (require-auth-or-agent.ts:131); on any expiry the stale in-memory body is `unregisterOpenClaw`'d so the next call short-circuits. Restore obeys the IDENTICAL rule (openclaw-session-restore.ts:356) + a belt-and-suspenders swept-gate (:365) — it can NEVER grant liveness the primary gate would refuse, never mints a new sessionId, never slides the TTL, never grants new ledger capability.
3. FAIL-CLOSED SCOPE = present && mismatch (NEVER null): the rotation/hash-rotation reject fires ONLY when `bot.sessionKeyHash` is PRESENT and `!== sha256Hex(sessionId)` (require-auth-or-agent.ts:166). A NULL hash is a not-yet-persisted freshly-minted session (partner register/PATCH calls registerOpenClaw Map-live BEFORE the explicitly-non-fatal hash persist) and MUST fall through to the TTL gate, never be locked out. Rejecting on NULL = the null-init lockout bug.
4. LEDGER-CAPABLE GATING: `config.ledgerCapable` is frozen at registration, defaults FALSE when omitted (fail-closed). RE-VALIDATED at resolve time: ledger-capable ONLY if `config.boundUserId === live row userId` (both non-null) (require-auth-or-agent.ts:280-294). A rebind to a DIFFERENT real user → demote to non-ledger AND `unregisterOpenClaw` (the stale-session ledger-theft backstop). A first-contact null→null session stays alive (can chat/perceive) but non-ledger.
5. NO-GUEST-FALLTHROUGH on the WRITE/money path: an agent session is 401 (unknown/expired) or 403 (non-ledger / no-bound-avatar) — NEVER silently demoted to the guest demo tier (the Rule E5 violation). Guests NEVER touch `avatars.clawTokens` (demo balance derived from the session row). Real CT flows ONLY for `isLedgerSubject` (user|agent) via `claw-token-ledger` on `avatar.id`.
6. SUBJECT-KEYING KEYSTONE (write == read): the WRITE path (`getSubject`) and EVERY READ/history/verify/claim path (`resolveSubject`) MUST resolve the SAME {user,agent,guest} via the SAME `resolveAgentSession` (require-auth-or-agent.ts:249). Drift = an agent's real-CT rows fall through to guest and vanish ('won 20 CT, no history' — the live 2026-06-21 prod slots/history defect). Every cove event is keyed `userId XOR guestFpHash` (cove_game_events_subject_check); user+agent collapse to ONE ledger subject on `userId`.
7. READ PATH IS DELIBERATELY WEAKER THAN WRITE: `resolveSubject`/`resolveActivityIdentity` soft-fall-through to guest on unknown/expired/non-ledger/unbound; the WRITE path 401/403s. Intentional — history keys on userId, reads NEVER spend, worst case is zero rows. Do NOT 'tighten' reads to throw.
8. PER-SUBJECT SERIALIZATION = mutex + advisory (BOTH, never one): a section mutating BOTH the DB AND a process-local Map needs BOTH `withKeyedMutex(subjectKey)` (covers the post-commit in-mem spawn) AND `pg_advisory_xact_lock` (cross-process, re-read row after acquire). Commit the bearer hash in the SAME tx as the row (atomic). Deadlock rule: outer lock first ALWAYS (agent → cap), nest inner. Commit-first-spawn-after.
9. LUCIA-COOKIE PRECEDENCE: `sessionMiddleware` (auth.ts) runs FIRST and populates `c.get('user')`; `requireAuthOrAgentSession` (:319) and `resolveActivityIdentity` (:193) both try the Lucia user/cookie BEFORE the `X-Clawville-Agent-Session` header. A logged-in human cookie ALWAYS wins over an agent header on the same request.
10. ALL RESOLUTION IS ASYNC: `validateLiveAgentSession`, `resolveAgentSession`, `resolveActivityIdentity`, and the cove `getSubject`/`resolveSubject` wrappers all do a DB lookup on the agent branch. A sync (un-awaited) call silently returns a truthy Promise and breaks subject resolution — always `await`.
11. ONE AVATAR PER USER: `avatars.userId` carries `.unique()` (avatars.ts). An agent and its bound human share ONE userId → ONE active avatar → ONE history scope; the agent never forks a parallel session. `ownerMatches` keys on `userId` for both subject kinds.
12. BEARER IS A REAL-CT CREDENTIAL: persist/log ONLY the one-way sha256 — full `sha256Hex` to `openclaw_bots.session_key_hash` (restore + rotation equality), 64-bit/16-hex `sessionDigest` to logs/ledger metadata. NEVER write the raw bearer to `events.session_id`, ledger metadata, or console. A digest is a correlation id, NEVER accepted as auth.
13. FINGERPRINT_SECRET HARD-REQUIRED + fp STABILITY: `fingerprint.ts` THROWS at module load if `FINGERPRINT_SECRET` is missing (:45) OR < 32 chars (:52) — crashes API boot. `fpHash` is the guest subject key and is ALWAYS non-empty (3-tier fallback). Tier-2 keys on the /24 `ipPrefix` (:107), NOT the raw IP, so a dynamic-IP guest keeps ONE fpHash across DHCP/CGNAT/VPN churn between writing an event and reading history. Same secret backs the dash-access HMAC — rotating it resets every fp bucket AND invalidates every cv_dash cookie.
